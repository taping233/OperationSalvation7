# 工程选题与验收计划

本页维护 Vite 工程任务的选题与验收方法。已确认方向见[章程](../project/CHARTER.md)，在途任务和证据见[STATUS](../../STATUS.md)。研究所第二地图暂缓；具体切片根据当前问题和测量结果选择。

## 下一轮目标与完成标准（2026-10-20）

本轮以**普通战斗结束 → 领取奖励 → 按需整理背包 → 返回原地图**为样本，完成一批范围明确、检查匹配、实页可验的流程改进，落实开发提效与流程标准化。先核对当前实现和已有证据，选取仍存在的具体问题；已经满足标准的部分直接复用。以下维护本轮验收条件，实际完成结果见“本轮验收结论”。

### 范围与已有基础

- 完整自然跑局已于2026-10-19由老板确认，沿用[路线图中的已有验收](../../roadmap.md)，不重新列为本轮待完成项。新改动影响相关整局边界时，按质量门补验受影响路径。
- 本轮覆盖该流程的奖励处理、背包整理、返回及恢复边界；共性界面问题优先修公共组件，再核对其实际消费者。以复现结果确定修改文件，不预先假定历史问题仍存在。
- 检查选择复用现有[改动核验工具](../../CHANGE-REVIEW.md)。只有实际批次证明存在漏选、重复操作或人工衔接缺口时，才补相应工具功能。
- 研究所第二地图及其满牌盒设计、地图生成硬约束、全套美术重绘和新增玩法不纳入本轮。未定玩法继续沿[PENDING](../../PENDING.md)处理，不用默认实现代替决定。

### 必须满足的条件

| 项目 | 完成时应看到的结果 | 验收依据 |
| --- | --- | --- |
| 问题与改动范围 | 每个纳入问题有当前版本的复现条件、修改前结果和明确预期；能区分已修复、仍复现与未验证。 | 同一批次的问题清单、相关源码与已有证据；无当前复现依据的旧问题不直接当作缺陷修复。 |
| 领取与资源结果 | 正常领取可完成；重复确认不重复发奖或扣费；满包时有可执行的处理入口和明确结果；领取、整理、取消或关闭后的卡牌、金币及剩余奖励符合对应现行规则。 | 相关行为回归与实页操作；涉及尚未确定的规则时保留该分支待决，不擅自定义奖励或付款语义。 |
| 返回与恢复 | 完成或离开整理后能回到正确的奖励界面或原地图，继续操作；重进及已有检查点刷新不导致重复结算、奖励丢失或残留遮罩。 | 返回、重进、重复输入及恢复的定向用例；对照[存档契约](../../save-format.md)核对落盘边界。 |
| 界面一致与可操作 | 领奖、整理和返回入口沿用现行公共组件及视觉规范；当前窗口下，长名称、满包信息和必要操作可读、可见、可点击。 | 当前平台内置浏览器的相关页面与真实操作；夹具和正常玩家路径分别标明，不把静态样板当作整段流程通过。 |
| 检查选择与集中验证 | 按本批实际路径给出检查计划；人工复核代码、样式、数据、资源消费者及动态入口，补齐适用检查；同一批次集中执行，未变化且环境相同的有效证据可复用。 | 既有 review/verify 输出、人工补选原因及真实退出码；门级别遵循[质量门](../../quality-gates.md)，失败、跳过和未执行分别报告。 |
| 提效证据与交接 | 一份批次记录能定位问题、改动、检查结果、实页证据与遗留；记录命令、必要人工步骤和实际耗时，说明消除了哪些重复操作。下一位制作者能按同一入口继续工作。 | 记录保存在该批次证据目录；使用同口径对照说明收益，没有可比基线时不宣称耗时降幅。现有工具已满足时以实际批次验证，不重复开发。 |

### 验收路径与结束条件

选取与改动有关的正常领取、满包整理、已有取消或关闭入口、返回重进、重复确认及检查点恢复场景，参考[玩家验收矩阵](../qa/ACCEPTANCE-MATRIX.md)的P03/P04/P07。随机分支可用补充档位或受控夹具核对，记录真实输入和来源；本轮不要求为凑覆盖重跑一整局。

上表适用条件全部有通过证据后，才能报告该轮完成。内置浏览器受阻、玩法未决或必需检查失败时，写明具体未完成条件和可继续的独立工作，保留为阶段结果；不把源码检查通过写成实页通过。新发现超出该流程的问题按现行规则进入候选或待决策项，不扩大本轮范围。

## 当前执行约定（2026-10-19）

按老板本轮要求，优先快速迭代完整玩家流程，合并相关体验问题后统一回归；减少逐小点整理证据、反复跑测试及等待 CI。已采用的开源工具用于发现和解决具体问题，不为工具分数增加无关工作。保留必要的数据安全检查、项目强制质量门和及时保存提交；不禁用 CI，已启动的 CI 跟到结果，同时推进下一批。交付先说明玩家可感受到的变化、覆盖页面及实页未核范围。此约定不改变提交权限和工具审批要求。批前核对改动文件是否被资源消费者指纹登记；命中时先审查静态/动态资源选择差异，再更新审查指纹并验证构建，避免安全回退重新打包旧资源。

## 选题要回答的问题

1. 当前底层最妨碍可靠修改的一个或两个边界是什么？用真实调用路径、失败案例和现有测试说明，而不是按文件长度挑目标。
2. 当前 Vite 页面在现行测试环境中的首屏、地图移动/缩放、战斗与长局表现如何？哪项开销在实际交互中最明显？
3. 改动后，后续人类或 Agent 制作者能否从一份明确入口找到模块归属、数据源、修改步骤和验证方法？

## 执行顺序与出口

| 顺序 | 工作 | 最低交付证据 |
| --- | --- | --- |
| 1 基线 | 记录时间、HEAD、工作区差异、依赖版本、当前窗口、设备与浏览器；在允许的环境测当前 Vite 实页及所选关键操作 | 可重复的采样步骤、原始记录、耗时/帧节奏/资源指标和明显卡顿场景；无法有效采样则写原因 |
| 2 选题 | 结合基线、架构守卫、存档失败边界与改动频率，选最多两个独立切片 | 每项列原问题、状态所有者、允许依赖、接口变化、风险与不会改变的玩法语义 |
| 3 实施 | 先补或复用失败样本，再改接口与调用方；性能改动保留前后同条件比较 | 定向行为/类型/架构检查，页面可见变化在当前窗口实页核对；结果与原始命令关联 |
| 4 交接 | 更新实际受影响的权威文档与制作步骤，注明兼容边界和未覆盖范围 | 下一位制作者能按文档定位源数据、调用入口、测试和失败恢复方式 |
| 5 收尾 | 交叉审查与阶段质量门；冻结可复现的结果快照 | 按项目约束报告定向、全量、构建、实页和性能各自的真实状态；未执行项不写通过 |

120 FPS 是努力方向，不是本轮未经测量就宣称通过的硬门槛。先建立当前 Vite 实页基线，再以相同设备、浏览器、窗口和采样步骤比较回归。若指标恶化，应解释可观察收益及取舍；若采样受系统负载干扰，应重测或标为无效。历史[性能文档](../../performance.md)中的 Electron 数据不能代替本轮网页版结果。
