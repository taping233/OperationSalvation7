## 工作目标与取舍

游戏体验与 Agent 工程是并重的两条长期主线。每一轮选一个能观察到结果的主问题，允许另一条主线承担必要的配套任务。老板已决定下一轮以代码为核心，着重底层可靠、性能、易修改和给后续制作者的明确文档。玩法方向与卡牌规则由老板决定；技术实现和验证方案由负责该任务的人提出并记录。

优先顺序：当前阻断或数据损坏风险 → 本轮主问题 → 已承诺的收尾 → 新想法。新想法先进入“候选”，写出替换哪项工作后再升为本轮任务。代码重构可以是本轮主问题，但要说明它改善哪种开发或实验成本、用什么证据判断。

## 每轮只记录这些信息

| 字段 | 填写要求 |
| --- | --- |
| 主问题 | 一句话说明要改变的玩家体验或 Agent 工程现象 |
| 交付边界 | 纳入、不纳入及涉及的文件/数据所有者 |
| 完成标准 | 可观察的游戏行为、实验结果或工程契约，不写“基本完成” |
| 任务 | 每项有单一负责人、前置依赖、对应验证与状态 |
| 证据 | 日期、Git HEAD 与工作区差异、测试或实页/实验记录、未核实项 |
| 收尾决定 | 保留当前方案、继续迭代、改变方向或搁置，并说明原因 |

执行阶段统一为 planned（计划）、doing（实施/验证）、complete-uncommitted（完成未提交）、partial（阶段结束有遗留）。候选归roadmap，待拍板归PENDING；障碍、未验范围与检查结果写task.json的unverified/checks，不另建状态副本。完成需负责人按doneWhen确认；旧报告只证明当时时点。

并行工作先确定文件归属。共享文件被其他会话占用时，先记录接口约定并使用自己的新文件，等集成窗口再处理入口；不覆盖在途修改。每轮结束整理本轮自有记录，列明 HEAD、与本地远端引用的差异、验证范围和未核实项。提交、推送、发布、回滚及任何删除遵守项目约束，不能由看板状态代替授权。

验证按改动选最小充分范围：规则用定向测试；玩家可见变化在当前平台内置浏览器当前窗口核对；Agent 策略使用同一代码状态、同一设置与种子的配对实验；公共架构或阶段收尾再走项目全量质量门。具体命令和边界以[现行质量门](../../quality-gates.md)为准。共享工作区有其他会话未提交改动时不运行构建。
