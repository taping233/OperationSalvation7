## 五项设计原则

| 原则 | 本项目中的具体要求 |
| --- | --- |
| 高效 | 同时关注运行开销和开发效率；复用现有性能预算与有效验证证据，涉及热点时对比实测，避免重复扫描、复制和不必要的全量检查 |
| 简洁 | 每条业务路径有清楚入口和结果；减少历史重复路径和层层转发，新增抽象要能解释其必要性，接口数量和调用深度保持可理解 |
| 解耦 | 规则和状态不依赖页面 DOM；跨模块通过显式命令、查询、快照或注入端口协作；读写权限和允许依赖可检查 |
| 可复用 | 从已经存在的相同行为提取稳定能力，优先供 UI、Agent、测试复用；明确不同调用方的语义差异，按真实需求抽象 |
| 模块化 | 模块具有单一且清楚的职责、状态所有者、公开接口、生命周期和独立验证入口，改动影响尽量局部化 |

## 3. 数据管理与卡牌规则

- 明确三层数据：内容定义（卡牌、地图、场景等）、运行状态（本局状态和派生缓存）、持久存档（档位和局外成长）。三者分别管理，不把 UI 节点或渲染缓存混入存档。
- 内容数据按类别明确唯一权威来源、生成关系、稳定 ID、引用校验和版本；逐步收口 JSON 与代码内定义的分散来源。制作流程形成“编辑来源 → 校验 → 同步/生成 → 回归”的可重复链路。
- 运行数据明确所有者和命令写入口；持久数据通过约定存储端口读写。保留现有版本迁移、冲突检查和恢复日志机制，补齐数据损坏与升级迁移的真实样本。
- 按首发需求评估本地存档备份、导出与恢复。云同步和数据库服务只在产品目标明确需要时设计，不作为当前单机数据管理的默认前提。
- 先根据实际运行卡库建立迁移清单，不能只统计 `cards-sync.json` 或 schema 字段来推断完成率。
- 按伤害、费用与注能、状态效果、抽牌与发现、装备与时点等机制逐族收口。
- 每张发行卡明确结构化规则来源；对照迁移前后的执行结果，检查边界和组合效果。
- 关键验证包括换文案不换效果、预览与结算一致、异步选择可结束、战斗中读档可继续。
- 已停止的制作坊开放/A4 不由本计划恢复。生成卡数据使用既有同步工具，不手改 `cards-sync.json`。

验收：明确范围的发行卡池不再以展示描述决定玩法；未支持效果明确失败；随机结果按同种子和同规则版本比较。数据校验可以发现缺失/重复 ID、错误引用和非法形状；存档升级及故障恢复不丢失或重复发放数据。旧执行分支的删除需另列路径获得同意。

## 技术路线与决策边界

- 当前执行范围只有 Vite 主线；Godot、Unity、EXE 保持冻结。暂不以迁移引擎作为提升质量的前提。
- 只有目标明确需要重度三维、复杂物理、其他平台能力，或现有工具经实测阻碍制作效率时，才重新比较局部改进与迁移成本。
- 不以通用自研引擎为独立目标；框架能力优先服务这款游戏。
