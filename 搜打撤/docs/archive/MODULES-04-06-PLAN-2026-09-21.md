依据：[模块契约](./GAME-MODULE-CONTRACTS-2026-09-21.md)、[整体改造方案](./GAME-TRANSFORMATION-PLAN-2026-09-21.md)、[前三模块实施计划](./FIRST-THREE-MODULES-PLAN-2026-09-21.md)。本轮执行老板明确要求的编号 M04、M05、M06。

## 1. 本轮要让玩家感受到什么

**回基地后，看得到自己的收藏与人物，能购买和摆放家具；出发前，知道下一局追什么，并能快速选好投入。**

上一轮重点解决保存、收藏和家具规则。本轮重点让这些能力出现在实际游戏里，形成可操作的基地样板，并接入目标与备战。样板资产与最终正式美术分开标注，不把灰盒或界面线框当成美术全部完工。

目标流程：

```text
进入基地空间
  → 点击收藏柜或快捷入口整理、收藏
  → 人物成长与收藏展示刷新
  → 购买家具，摆放、取消或保存
  → 选择最多三个追踪目标
  → 编辑、预览并应用一套带入预设
  → 使用现有出征流程开始游戏
```

最终房间风格仍需制作人看样张确认。正式美术铺量不先于方向确认；M05 可先用明确标注的灰盒与既有素材，把真实数据和操作闭环做出来。

## 4. M04：先做出统一而可实施的视觉样张

### 具体工作

1. 基地采用固定三分之四视角的单室空间，落实出征台、仓储墙、收藏柜、休息角、宠物角五个区域。
2. 四页样张统一信息层级和交互状态：基地、收藏、备战、战斗提示。使用真实卡名、数量与人物信息，不用占位文案掩盖排版问题。
3. 沿用项目已定画风、人设、字体与颜色语义；采用现有合适素材配合明确标注的原型元素，不重新定义角色外观。
4. 把六家具拆成分别可消费的视觉条目，约定投影、逻辑占地、图像轴心、遮挡顺序和缺图回退；其中灯按 M03 当前桌灯支撑规则表现，不擅自改成另一种家具。
5. 让商店、升级、成就等原有功能都有可见入口，不能为了漂亮场景把功能藏起来。

### 输入与输出

- 输入：M03 的房间／家具目录、M05 的热点需求、当前角色与卡牌素材、真实 UI 状态。
- 输出：`home.visuals.js` 的视觉元数据，`docs/previews/m04/` 下四页可浏览样张，可分离的原型素材与清单，以及 `docs/modules/M04-DELIVERY.md`。
- 接口：`VisualPack` 包含版本、房间投影、`AssetSpec[]`、UI token、交互状态、预览和源文件路径。
- 资产清单明确区分“已有正式素材”“本轮候选”“灰盒／原型占位”。

### 验收与停止点

- 两种视口（1920×1080、1280×720）下，真实长卡名、空／满仓、缺钱、未解锁状态可读，主要按钮不遮挡。
- 五热点和全部旧功能入口有明确位置；前景家具不能遮死操作区域。
- 文件路径、尺寸、轴心与层级可验证；家具不是只能从合成大图里裁出来。
- 四页可直接打开审阅，不只提交文字设计说明。
- 本包停止于方向样张、可消费视觉规范和原型视觉包；最终新增房间／家具正式图待制作人选定方向后另行铺量。M04-D 的制作人确认保持待验收状态。

## 5. M05：让真实基地能够进入、操作和保存

### 具体工作

1. 在当前游戏里增加基地空间入口，使用项目锁定的 PixiJS 版本；列表、说明和复杂操作保留 DOM 面板。
2. 做出房间、家具、人物与收藏展示的层次关系；首位人物可复用现有图或帧，不等待骨骼动画项目。
3. 五个热点和快捷按钮打开同一套功能，保证仓库、人物、商店、升级、收藏和出征仍便捷可用。
4. 把 M02 的真实收藏转换与皮肤保存接入旧界面；成功后才播放反馈、刷新数据，不再从 UI 重复发经验。
5. 把 M03 接成可购买、可摆放、可取消、可保存的操作；两展位读取永久收藏，卡牌实物耗尽后仍可展示。
6. 接入 M06 的追踪目标、预设编辑和应用入口。M06 未就绪时先完成其他真实操作，并保留明确挂载点；不能最终忘记集成。

### 输入与输出

- 输入：M01／M02／M03 真正的只读视图和业务命令，M04 视觉包，M06 可挂载组件。
- 输出：`home.scene.js`、`home.presenter.js`、`home-scene.css`，当前 `game.hub.js` 的有界接线，测试和 `docs/modules/M05-DELIVERY.md`。
- 场景接口：`mountHome` → `update`／`setActive`／`dispose`。
- 场景只发送意图；扣钱、扣卡、保存全部走现有模块命令。保持预览状态与已保存状态分离。

### 验收与停止点

- 从实际游戏入口进入基地，完成收藏、展位选择、家具购买和布局保存；重开后读取同一结果。
- 保存失败能说明原因且不伪装成功；摆放取消不写档，非法摆放给出具体反馈。
- 两种视口下可见位置与点击位置一致；弹窗打开后不会点穿到房间。
- 连续进出十次没有画布、监听器或 ticker 累积；进入战斗或隐藏基地时暂停更新。
- WebGL 不可用仍能使用 DOM 功能入口并出征。
- 本包停止于一室可操作样板和现有功能接通，不扩多房间、角色寻路、自由镜头或生产排班。

## 6. M06：让下一局有目标，让准备投入可比较

### 具体工作

1. 最多追踪三个目标，保存到当前档位；玩家能取消、替换并看到目前的收集状态。
2. 每个展示来源都有实际卡池或事件条件依据。暂时不能确认的明确显示“来源未确认”，不杜撰掉率或保证必得。
3. 两套可编辑预设，可命名为“猛攻／跑刀”，也可改名；它们只是带入方案，不增加强制游戏模式。
4. 预览列出已有、缺失、禁带和投入信息，核对角色及宠物资格。缺货愿望可以保存，但不能伪装成已经备齐。
5. 应用预设前再次检查当前库存和状态，合法时写入当前准备选择；保留现有出征流程，不偷偷换卡或减少数量。

### 输入与输出

- 输入：M01 档位快照，M02 收藏／人物视图，真实卡池来源和带入规则。
- 输出：`preparation.commands.js`、`preparation.sources.js`、`preparation.view.js`、`preparation.css`，定向测试和 `docs/modules/M06-DELIVERY.md`。
- 接口：`getSources`、`setTrackedGoals`、`savePreset`、`previewDeployment`；UI 提供挂载、更新、卸载与应用预设回调。
- 持久化使用 M01；皮肤使用 M02，不另造第二份状态。

### 出征依赖的明确边界

契约中的 `startDeployment` 要由 M11 负责真正扣除带入与创建对局。M11 和 M01 跨键扩展尚未完成，因此本轮不私造一套新开局事务，也不把旧 `newRun` 包装后宣称满足跨重启幂等。

本轮可以完成目标、预设保存、预览和应用到原准备选择；`startDeployment` 只提供可注入 M11 的适配口，未提供依赖时返回明确错误。原有出征功能保持可用。**M06-C 中“跨重启重复开局只生成一个 runId”的真实接入验收延期到 M11，使用替身通过不代表该项完成。**

### 验收与停止点

- 第四个追踪目标报上限，原有三个保持；重复目标去重，切档不串数据。
- 有货、缺一张、全缺和职业禁带分别给出正确预览；重复查看不扣卡、不改 RNG。
- 预览后库存变化，应用前重验并解释冲突。
- 预设编辑保存、重载、改名和应用可从实际页面完成。
- 所有已展示来源逐项对应代码／配置证据；未知不伪造。
- 本包停止于目标与准备组件真实接入、M11 接口边界明确；不扩新地图、剧情奖励、掉率或全局经济平衡。
