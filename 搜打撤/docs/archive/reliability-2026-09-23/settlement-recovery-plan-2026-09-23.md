## 数据和接口

- 复用 `recovery.commands.js:commitBaseAndRun` / `readSettlementReceipt` / `recoverSlot` 与 `recoverable-pair.js`；不另建通用事务机制。
- `recoverSlotIfPending(slotId)`：无恢复日志时不要求 Web Locks；有日志时必须走锁与校验，失败阻止读档，不把坏日志当作空档。
- 顶层 `pendingExtraction` v1 保存 `runId`、`phase: organizing`、请求序号、剩余卡牌、已确定的消耗口袋保留结果和资源摘要。begin/入库/finish 的写入通过两键命令，普通 saveGame 不写整理中的快照。
- `validatePendingExtraction` 提供纯结构校验；`resumeExtraction` 同步恢复整理页面，由 boot 注入 session，session 不反向导入页面模块。
- 内存 `terminalPending` 在死亡/放弃命令进行中及失败待重试时阻止自动保存；正式结束以持久回执为准，不能先删档再发奖。
- XP、统计、仓库和龙巢解锁进入同一次基地草稿；不得在事务外再调用会写存档的旧 `Meta.track` / `unlockNest` 重复结算。

## 验收要求

1. 日志首写、基地写、运行档删除、阶段日志和清理失败分别验证；重启恢复后奖励仅一次。
2. 失败不覆盖旧档，不把失败显示为成功；旧回调不能提交到新的 slot/run。
3. 整理页刷新不丢待入库牌、不重掷口袋概率；完成后刷新进入基地。
4. 新增字段须兼容无字段旧档；无锁环境不得把正式两键结算降级成多个裸写。
5. 干净工程候选单独验证，其他会话的 TT12 / UI / 照相馆改动不混入提交。生产构建只在隔离 Vite 目录执行，性能预算不放宽。

## 集成时补齐的边界

- 异步恢复前记录对局身份；恢复或提交返回后复查档位和对局，旧页面回调不得覆盖新对局。
- `extractionPending` 在开始撤离及失败待重试时阻止普通自动保存；成功后转为持久 `pendingExtraction`。读档与新局清除旧内存标记。
- 重试先查原请求回执，再要求运行档存在；完成结算已经删除运行档时也可正确重放成功结果。
- 没有选中档位的开发测试仅更新内存，不能因为 `Base.slot` 还记着先前档位而写入正式存档。
- 旧撤离测试改为导入真实 ESM 模块，不再截取函数源码执行；保留献祭、取消、仓满和口袋概率的行为断言。
