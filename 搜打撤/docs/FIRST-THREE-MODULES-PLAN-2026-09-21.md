# 第一批实施计划：M01 存档、M02 收藏成长、M03 家具布局

日期：2026-09-21｜协调与复核：Friday｜执行：3 个 Sol 子代理

依据：[模块契约 v1.0](./GAME-MODULE-CONTRACTS-2026-09-21.md)、[整体改造方案](./GAME-TRANSFORMATION-PLAN-2026-09-21.md)。本轮按老板“前三个模块”指令，执行编号 M01、M02、M03。它们与契约中的第一实施波次 M04-a／M05-a／M01-a 不同；本轮以这次指定的模块范围为准。

## 1. 这一轮要得到什么

**做出能独立验证、能接入现有游戏的养成与装修业务基础：东西归谁、花钱是否成功、收藏给了什么、摆在哪里、重开后是否还在，都有明确答案。**

三个模块连起来的目标流程是：

```text
读取真实基地档
  → 消耗实物卡，登记收藏并结算既有成长
  → 读取永久收藏，选择展示对象
  → 使用现有储备币购买家具，校验并保存布局
  → 重新加载，同一档位结果保持一致
```

这轮首先交付业务接口、配置、持久化和对应验收。最终 2.5D 房间画面、鼠标拖放、家具正式图仍由 M04／M05 承接，不能把本轮的业务基础宣称为房间已经制作完成。收藏界面的原有功能继续可用；新增接口接入界面的改动统一交 Friday 复核后处理。

| M02 | `sol_m02_collection`／`gpt-5.6-sol` | 收藏转换、人物成长查询、永久记录与实物区分、皮肤持久化 | 老界面和新基地都能调用同一份收藏／成长逻辑 |

## 3. M01：先让新功能能够可靠保存

### 要做的事

1. 从现有 `base.js` 读取真实五档结构，补齐 `home`、`appearance`、`goals`、`story` 缺失字段；不复制现有仓库、收藏和经验。
2. 提供 `readBase(slotId)`，返回可独立使用的只读快照。
3. 提供 `commitBase(context, preparedChange)`，让一次业务操作提交完整结果；存储失败时不留下内存已经扣钱、盘上没有保存的半笔操作。
4. 持久保存请求身份：同一次操作重复提交或重启后重试，不再扣款／扣卡；状态过期则要求重新读取。
5. 兼容现有 `Base.save()` 调用，明确旧路径与新提交路径的修订号关系，避免双方静默覆盖。

### 输入和交付

- 输入：当前基地档、现有兼容样本、M02／M03 产生的业务变更。
- 交付：`base.commands.js`、`base.js` 的最小适配、定向测试、`docs/modules/M01-DELIVERY.md` 交付报告（由代理完成时生成）。
- 消费接口约定：`Context = {slotId, requestId, expectedRevision}`；变更包含 `beforeRevision`、`command`、`payload`、`afterState`、`events`。最终细节由提供方与两个消费方共同核对。

### 通过标准

- 旧档加载前后原资源、卡牌和永久进度不变；缺新字段能正常补齐。
- 档位 1 的装修不影响其他四档。
- 模拟存储写入失败，库存、钱、布局在内存和重新加载后都保持提交前值。
- 同一请求只执行一次；换参数沿用同一请求 ID 报错；过期的新请求不执行。
- 损坏档或未来版本不被误认成空档覆盖。

**停止点：**满足契约 M01-A～D 对本轮基地范围的保证。跨基地／对局两键事务 M01-E 后置，不能为了这三个模块先重写整个存档系统。

## 4. M02：把收藏与成长变成独立、可信的能力

### 要做的事

1. 将现有收藏规则适配为可直接调用的接口，而非只能通过界面按钮执行。
2. 明确区分实物数量和永久登记：消耗实物可以增长经验，首次登记只发生一次；展示永久记录不会生成实体卡。
3. 一次收藏把扣卡、首次登记、既有经验和解锁变化作为同一笔业务结果提交。
4. 提供人物当前成长与下一项奖励信息，满级时明确返回满级状态。
5. 把皮肤选择放入所属档位保存，保留当前已经可用的皮肤；没有某场景贴图时按既定素材范围回退。

### 输入和交付

- 输入：M01 快照、真实卡牌／人物配置、现行收藏和里程碑规则。
- 交付：`collection.commands.js`，必要的 `meta.js`／`art.js` 小范围适配，测试、`docs/modules/M02-DELIVERY.md` 交付报告（待代理生成）。
- 接口：`getCollection`、`getCharacter`、`convertCollection`、`selectSkin`；返回明确的消耗、经验变化、首次登记和奖励结果。
- 另交现有 `game.hub.js` 的接线说明，避免同时改共享页面。

### 通过标准

- 两张同种职业卡分两次收藏：实物 2→1→0，首次登记一次，经验按现行规则增长两次。
- 同请求重试不重复消耗或发经验；不足数量整笔失败。
- 实物归零后永久记录仍能展示，不能再从展示中取出战斗用卡。
- 里程碑不重复发奖，且保持现有主动领取／自动结算语义。
- 皮肤选择重载后保持；无效皮肤报错；已有可选皮肤不被重新锁住。
- 注入存储失败后无部分扣卡、部分加经验。

**停止点：**业务模块独立验收、当前 Base 的真实依赖接入和必要旧路径兼容通过；不改等级上限、经验曲线、角色身世，不新增好感度或奖励大表。

## 5. M03：做出可摆放、可保存的装修规则

### 要做的事

1. 定义一间公共室与六件家具：展示柜、工作桌、座椅、灯、地毯、墙饰。
2. 使用现有储备币购买；家具价格作为可配置的样板值记录，尚不宣称已经完成经济平衡。
3. 用逻辑网格定义家具占地、摆放区域、方向、重叠规则和支撑关系。
4. 实现购买、保存布局、设置／清空展位；两展位只引用永久收藏。
5. 给后续场景提供稳定的家具实例 ID、位置和展示数据，做到更换图片不会改变拥有权和价格。

### 输入和交付

- 输入：M01 快照与提交门面、家具目录、M02 永久收藏记录。
- 交付：`home.catalog.js`、`home.commands.js`、测试、`docs/modules/M03-DELIVERY.md` 交付报告（待代理生成）。
- 接口：`getHome`、`validateLayout`、`buyFurniture`、`saveLayout`、`setDisplay`。
- 本轮不生成正式美术；配置和逻辑可以用代用矩形独立验证。

### 通过标准

- 购买扣除准确金额、增加准确数量；重试不重复购买，钱不足则两者都不变。
- 越界、非法方向、冲突、超出拥有量和不合法支撑返回具体原因，并保留原布局。
- 地毯等特例有明确配置，不能靠代码碰巧允许重叠。
- 布局保存和重载完全一致，预览取消不写档。
- 已登记但实物为零的收藏可展示；未登记收藏不能展示；设置展位不扣卡、不增卡、不加经验。
- 不购买家具也能使用现有仓库、人物和出征功能。

**停止点：**家具与布局业务接口可被实际基地档调用，固定样例验证通过；不做生产排班、家具战力、离线收益、完整场景编辑器。
