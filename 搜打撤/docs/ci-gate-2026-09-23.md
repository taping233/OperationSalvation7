## 2. workflow 设计要点（ci.yml）

- 触发：`push`（仅 master）+ `pull_request`（仅目标 master，即 merge 进 master 前必须绿）。
- 单 job `test`，`ubuntu-latest`，`timeout-minutes: 30`（本地全量约 4 分钟，余量充足，防挂死吃满 6 小时默认上限）。
- `permissions: contents: read` 最小权限（与既有 vite-quality.yml 口径一致）。
- 步骤：`actions/checkout@v4` → `actions/setup-node@v4`（Node 20，`cache: npm`，`cache-dependency-path: 搜打撤/package-lock.json` 指向子目录锁文件）→ `npm ci` → 全量测试。
- `working-directory: 搜打撤` 用 job 级 `defaults.run` 设置，四步全部生效（uses 步骤不受影响也无需生效）；中文路径在 Actions 中按 UTF-8 处理，既有 vite-quality.yml 已用同样写法。
- 测试命令按老板口径直调：`node node_modules/vitest/vitest.mjs run --no-file-parallelism`（绕开 vitest 不在 `node_modules/.bin` 的问题，也不依赖 npm scripts）。

### 直调命令绕过 pretest 钩子——已核实安全

`npm test` 自带 `pretest`（`narrative:compile` + `validate:data`），直调 vitest 不会执行它们。已核实 `game/src/generated/`（narrative-events.js、art-manifest.js、thumb-manifest.js）均为 git 已跟踪文件，干净 checkout 后直接可跑，不依赖编译产物；数据/叙事新鲜度校验仍由既有的 `vite-quality.yml`（其 `npm test` 带 pretest，另有 build+性能预算）覆盖。两个 workflow 职责互补：ci.yml=纯测试门禁，vite-quality.yml=全流水线。

## 4. 启用步骤

一句话：ci.yml 随下次推送到 GitHub（commit 进 master）即自动生效，之后每次 push master 与 PR 进 master 都会跑。

要把「绿」从信号变成硬门禁，还需在 GitHub 仓库设置 master 分支保护规则里勾选要求 check `Full test suite`（job 显示名）通过才能 merge——此操作属仓库设置改动，按边界由老板亲自执行。

## 5. 启用前置条件

1. ci.yml 需先 commit 并推送（等老板明确指示，本次未做）。
2. `npm ci` 要求 package.json 与 package-lock.json 严格同步。截至本文写入，工作区有另一会话未提交的 `搜打撤/package.json`（新增 eslint、typescript devDependencies）与 `package-lock.json`（+1374 行）改动，两者看 diff 是同步改的；但推送时必须保证二者一起进库，否则 CI 第一步 `npm ci` 就红。
3. 分支保护规则（见上节）由老板在 GitHub 设置中配置。

## 6. 坑与备注

1. **本地 Node 24 vs CI Node 20**：基线在本机 v24.13.0 跑绿；CI 固定 Node 20，若后续用只有更高 Node 才有的 API 会在 CI 暴露差异。既有 vite-quality.yml 用的是 Node 22，三个版本并存是现状，未统一（未核实是否需统一，属玩法/工程决策，不动）。
2. **双 workflow 并行**：push master / PR 会同时触发 ci.yml 与 vite-quality.yml（后者带 paths 过滤，只在你动过游戏相关路径时跑），互不冲突，job 名不同。
3. **Windows 本地 `npx vitest` 不可用**：vitest 不装进 `node_modules/.bin`（shim 缺失），故 CI 也统一用直调方式，本地/CI 命令逐字一致，避免环境差。
4. **cache 首跑无缓存**：`actions/cache` 首次运行未命中属正常，`npm ci` 全量安装约 1–2 分钟，之后命中缓存会明显加快。
