# R0 进出局与结算规则基线审计

日期：2026-09-21  
模式：只读代码审计；本文件是唯一新增产物。  
基线：`master` / `2dfec66aa610d9a1abc87a8ce1159ca2db90911d`，包含工作区现有未提交模块改动。

## 1. 本轮采用的最新明确规则

老板本会话原话优先于旧文档、旧注释和当前实现：

> 职业卡只能被带入无法被带出；本局收获和带入资源都会损失，但永久收藏记录/解锁保留，带入稀有卡可能永久失去。

本审计只把原话能直接确定的内容当定版：

1. 职业卡可进入对局，但不能作为实物从对局带回基地。
2. 失败结算必须真实损失本局收获和带入的实物；带入的稀有卡也可能永久失去。
3. 永久收藏记录和永久解锁不随实体卡损失而删除。

原话没有明确回答以下问题，因此本包不替老板推断：成功撤离时非职业带入卡是否全部可回收；安全格和珍珠盒在死亡、主动放弃时是否仍保留任何实物；消耗口袋在成功撤离时是否继续按 1/3 回收；职业卡失去实物后如何获得永久收藏记录。

## 3. 当前代码的真实行为

### 3.1 出征与职业卡进入对局

- 新准备命令在 `game/src/preparation.commands.js:61-87` 读取仓库数量，但 `:71-73` 把 `rarity === '职业'` 标为 `CLASS_CARD_FORBIDDEN`；`:120-128` 因预览不可开始而拒绝调用 M11。这与新规则相反。
- 旧基地准备页在 `game/src/game.hub.js:452-466` 直接过滤职业卡，`:542-543` 再次拒绝选取。
- 旧出征执行在 `game/src/game.session.js:591-613` 第三次拒绝职业卡；并且按显示名查堆、逐张立刻 `takeStashCards()`，不是稳定 `stackKey` 的单次事务。
- 选角色会自动获得两张本职业卡，`game/src/game.run.altar.js:323-350` 将其放入 `ownedCards`，且标记 `brought: 1`。这证明当前游戏已有一种“职业卡进入对局”的自然路径，但没有区分“基地带入”和“角色开局生成”两个来源。

结论：当前运行时一方面禁止基地职业卡带入，另一方面每局自动生成职业卡并统一标成 `brought`。仅翻转一个禁带判断会让两种来源混在一起，结算无法准确解释损失。

### 3.2 成功撤离与紧急撤离

- 第三层紧急撤离和第四层终局撤离最终都调用同一个 `doExtract()`：`game/src/game.run.altar.js:631-706`。
- `doExtract()` 在 `:716-720` 先把对局置为结束并删除进行中存档；随后才在 `:724-759` 写基地、抽取口袋并生成整理列表。写入任一步失败时，没有可恢复的原对局，也没有幂等收据。
- `:751-758` 把所有 `ownedCards`（只排除初始攻击）放进可入库整理列表，没有排除职业卡，也没有按 `brought` 来源区分。因此当前职业卡，包括选角生成的两张职业卡，都能成功带出。
- `:829-878` 的手动、全部和智能整理都可把职业卡写入仓库；仓库满时未选中的卡在完成整理后丢失。
- `:724-748` 自动带回 `inventory` 中的基地物资；消耗口袋逐张以 1/3 保留，再写入基地 `pocket`。`:749` 记录撤离统计。局内币不带回，玩家文案见 `:803-819`、`:890-898`。

结论：成功撤离明确违反“职业卡无法被带出”。至于非职业带入卡和本局收获在成功撤离时是否仍可带出，最新原话没有给出足以覆盖“成功撤离”语境的细分答案，下一包应保留为显式规则参数，不自行扩大损失。

### 3.3 死亡路径

- `game/src/game.session.js:114-130` 在结算前先 `runActive=false`、`clearSave()`，然后才向基地 `depositCards()`；同样存在写失败后既无对局档又无完整基地结算的风险。
- `:125-129` 会保存所有 `safe` 卡，不排除 `brought`；如果珍珠盒在安全格，所有 `stored` 卡也保存。
- `:131-149` 的玩家文案明确承诺安全格和珍珠盒抢运。
- `inventory`、局内币和 `usedPocket` 没有写基地，因此死亡时丢失。

结论：死亡当前允许带入卡通过安全格返回，也允许本局所得通过安全格或珍珠盒返回。若老板原话中的“都会损失”适用于失败结算，这两项直接冲突；但安全格/珍珠盒最终是否完全失效仍需老板明确，不能只靠旧注释决定。

### 3.4 主动放弃路径

- 玩家说明在 `game/src/game.menu.js:635-648`：带入卡全部丢失，本局获得卡只有安全格保留。
- 实现在 `:664-689`：先删对局档，再将 `safe && !brought` 的卡写基地；带入卡即使安全也丢失。
- 珍珠盒 `stored` 卡通常没有 `safe`，此分支也没有死亡路径的 `boxSafe` 规则，所以主动放弃时盒内资源不会跟随安全盒返回。死亡与放弃对珍珠盒处理不一致。

结论：主动放弃已经满足“带入实物会损失”，但仍保留本局安全格收获；若“本局收获都会损失”覆盖主动放弃，则此处也冲突。死亡和放弃的安全格/珍珠盒语义目前不一致。

### 3.5 消耗口袋与下一局

- 战斗消耗卡进入局内 `usedPocket`；成功撤离时 `game/src/game.run.altar.js:725-748` 仅 1/3 写入基地口袋，职业卡由 `game/src/base.js:403-413` 丢弃而不会进入基地口袋。
- 死亡和主动放弃不提交 `usedPocket`，因此全部损失。
- 下一次出发在 `game/src/game.session.js:659-663` 清空仍未复原的基地口袋。

这部分与“职业卡不能带出”一致，但成功撤离的 1/3 规则是否继续保留，不能从本轮原话确定。

### 3.6 永久记录与解锁

- 以上三个结算分支都没有删除 `Base.data.collection`、卡背、人物或其他基地解锁；永久记录通常会自然保留。
- 但是成功、死亡、放弃都先删除运行档，再分步写基地。持久化失败可能造成“实体与统计只写了一部分”的结果，现有代码不能给出强事务保证。
- 首脑成功撤离会在 `game/src/game.run.altar.js:744-749` 解锁龙巢并记录统计；它们与物资、卡牌、对局关闭不是一次原子提交。

## 4. 职业收藏的入口缺口

当前职业收藏的自然入口是“职业卡先进入基地仓库，再从仓库消耗实物完成收藏”：

- `game/src/game.hub.js:905-958` 与 `game/src/collection.commands.js` 的 M02 门面都以仓库 `stackKey` 为消费来源。
- `game/src/meta.js:129-143,201-215` 只定义哪些职业/能力卡可计入收藏和经验，不定义战斗中自动登记。
- 当前职业卡进入仓库的主要自然路径正是成功撤离整理，因为 `game/src/game.run.altar.js:751-878` 允许职业卡入库。

如果严格执行“职业卡只能被带入、无法被带出”，这个自然入口会消失或大幅缩窄。不能据此自行发明“获得/击杀/选角时自动登记收藏”、永久复制一张职业卡、或把局内职业卡直接兑换经验；这些都会改变 M02 的实物消耗、重复收藏与成长经济。

因此 R0-b 不能同时直接落地“职业卡绝不带出”和“现有职业收藏照常可推进”，除非老板先选择一个明确入口。可选项应单独提案，例如是否由特定结算收据登记、是否存在基地来源、是否允许仅首次永久记录；本审计不推荐也不预选其中任何一个。

## 6. 下一包最小可实施方案

### 6.1 先决策，再落码

先由老板确认两项，否则 R0-b 只能纠正文档和玩家文案，不能安全改经济：

1. 死亡与主动放弃时，安全格和安全珍珠盒是否仍能保住任何卡；若能，保住的是“本局获得”、 “基地带入”还是两者。
2. 职业卡禁止带出后，永久职业收藏的合法获得入口是什么。没有答案时不得自动登记、复制或发经验。

成功撤离的非职业卡、物资与口袋沿用现行规则，除非老板明确把“本局收获和带入资源都会损失”也定义为成功撤离规则。

### 6.2 接口

新增纯规划与单次提交边界，避免 UI 分支各写一套：

```ts
planSettlement({ runSnapshot, outcome, ruleVersion }): SettlementPlan
// outcome: 'extract' | 'death' | 'abandon'
// 每个实体条目必须保留 cardId/instanceId、origin、zone、rarity、reason
// origin: 'base_brought' | 'run_reward' | 'class_grant' | 'starter'

settleRun(
  { slotId, requestId, expectedBaseRevision, expectedRunRevision },
  { runId, outcome, planFingerprint }
): Promise<Result<SettlementReceipt>>
```

`SettlementReceipt` 至少包含 `recovered[]`、`lost[]`、`permanentUnchanged[]`、`resourceDeltas`、`runClosed`、`ruleVersion`。规划是纯函数；执行时重新核对真实 run/base 修订号。相同请求跨重启返回同一收据；同 ID 换参数报 `REQUEST_ID_CONFLICT`；过期报 `STALE_REVISION`。

写入必须通过 M01 扩展的跨基地/对局提交：基地写入成功和对局关闭必须成为一个可恢复事务，不能先 `clearSave()` 再逐项 `Base.save()`。任何写失败返回 `SAVE_FAILED`，旧基地和可恢复对局保持不变；事件只在提交成功后发布。

### 6.3 有限文件所有权

- M11 单一负责人：新增 `game/src/settlement.commands.js`、对应 `tests/r0b-settlement*.test.js`。
- 出征来源标记与实际扣仓库：`game/src/preparation.commands.js`；不要继续扩展按卡名处理的 `game.session.js:applyDeployPicks`。
- 三个旧分支的最小接线：`game/src/game.run.altar.js`、`game/src/game.session.js`、`game/src/game.menu.js`，只改为调用同一结算门面并渲染收据。
- M01 负责人独占 `base.commands.js`、`game.storage.js`/运行档事务扩展；M11 只提交计划，不另写 localStorage。
- 玩家规则文档：`docs/rules.md` 与 `docs/GAME-MODULE-CONTRACTS-2026-09-21.md` 在规则决策后同步修正。`game.hub.js` 与 `preparation.view.js` 的旧禁带文案由对应 UI 接线负责人最小更新。

不改卡池、来源概率、卡牌价格、收藏经验、口袋概率或安全格容量。

### 6.4 基于明确规则的样例期望

无需等待额外决策即可固定：

1. 职业卡 `class_grant` 或合法 `base_brought` 出现在成功撤离结算时，收据进入 `lost`，原因 `CLASS_CARD_CANNOT_EXTRACT`，基地不增加该实体。
2. 基地带入的一张稀有非职业卡在失败结算且不属于老板随后确认的保护例外时，进入 `lost`；基地原堆已在开局扣除，因此它永久失去。
3. 任一失败/成功结算前后的 `collection`、已解锁皮肤、卡背和永久剧情记录逐项相等；结算不得因实体丢失删除记录。
4. 重复 `settleRun` 同请求返回相同 `SettlementReceipt`，仓库、统计、解锁只变化一次。
5. 保存失败时 `runClosed=false`，基地无部分入库，重启后仍能重试原结算。

需要老板回答后才能固定：安全格与珍珠盒在 death/abandon 下的 recovered/lost 期望；成功撤离的非职业带入卡、本局奖励和消耗口袋期望；职业永久收藏的新入口。

### 6.5 玩家可见验收

- 出发前逐张显示“此卡离局时的风险”，职业卡明确写“可带入，任何撤离结果都不会作为实物返回基地”。
- 结算页按来源列出“带回 / 永久失去 / 永久记录保留”，稀有带入卡必须点名，不只显示数量。
- death、abandon、第三层紧急撤离、第四层成功撤离各走一次真实流程；重开后仓库、收藏、解锁和收据一致。
- 人为制造一次存储失败，页面提示结算未提交且可重试；不得出现已经回标题但奖励未落盘的状态。

## 7. 审计结论

当前 M11-B、M06 准备规则和多处玩家文案均与老板最新职业卡方向相反；成功撤离会把职业卡带回，死亡会抢运安全格中的带入卡，主动放弃会保留安全格中的本局收获。三个结算分支还存在先删对局档、后分步写基地的共同事务缺口。

R0-b 可以先实现来源标记、纯结算计划、事务与收据框架，并纠正职业卡“可带入、不可带出”的方向；但在职业收藏新入口、安全格和珍珠盒失败语义得到老板确认前，不应宣称完整规则迁移已经可直接落地。
