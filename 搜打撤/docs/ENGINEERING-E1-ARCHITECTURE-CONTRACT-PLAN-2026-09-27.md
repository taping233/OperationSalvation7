## 3. 已确定的顶层方案

沿用当前 Vite 单机客户端和已有功能目录，采用模块化单体。以下是逻辑职责，不要求按本表重新搬目录。

| 职责区 | 责任 | 允许的协作方式 |
| --- | --- | --- |
| 界面与输入 | 页面、渲染、演出、音效、玩家输入和 Agent 输入适配 | 发送所属功能域命令，读取只读观察结果；只拥有展示状态 |
| 应用流程 | 出征、移动、战斗、选择、结算、恢复的先后顺序和生命周期 | 调用领域入口和注入端口；决定取消、互斥、检查点及何时报告成功 |
| 游戏规则与状态 | 规则计算及本局、战斗、基地各自的权威状态 | 每类状态有唯一所有者；跨域通过公开命令、查询或命名端口协作 |
| 内容数据 | 卡牌、敌人、事件、地图定义与版本 | 稳定 ID、结构化规则、生成来源和运行时校验；展示文案独立于规则效果 |
| 存储与基础服务 | 本地保存、迁移、恢复、随机流和必要诊断 | 通过明确端口注入；启动入口装配具体实现，核心规则不依赖 DOM 或存储全局 |

具体约束：

1. 玩家与 Agent 对同一业务行为使用同一入口和规则校验。接口按功能域组织，沿用现有命名命令，不增加无必要的万能转发层。
2. 局内资源、地图位置和背包；战斗回合、牌堆、临时效果；基地资产与成长分别明确所有者。已有共享字段需标明真正写入口，不能另建第二份权威状态。
3. 观察快照不允许改变真实状态。同一活动会话的互斥操作遵守既有队列和守卫；旧会话的异步结果不得修改新会话。
4. 同一结算重复请求不能重复发奖。保存成功、操作成功、待恢复和失败须按真实接口区分；不能把结构校验误称业务成功。
5. 保留已验证的存档、地图快照、随机流与版本兼容语义。确定性比较必须约定规则/内容版本、初始状态、随机状态及操作序列；演出速度不能改变约定的规则顺序或随机消耗。
6. UI 暂态、动画中间态及可重建渲染缓存不作为存档权威数据。保存时点遵循已有稳定检查点，不统一改成每个操作立即写盘。
7. 继续使用 JSDoc、checkJs 和必要的类型声明，先覆盖高风险接口；后续仅按明确收益逐模块评估 TypeScript。静态类型与外部输入、内容、存档的运行时校验各司其职。
8. 新类型必须进入真实检查范围并约束真实调用。不能通过无依据的 any、忽略诊断、关闭检查或空泛包装制造通过；现有成功结果无需强制改成统一形状。
9. 新旧实现共存时必须有唯一权威状态、明确转接关系、调用方清单、旧路径退役条件及失败恢复责任。删除和回滚实施依旧另需明确授权。
10. 优先复用 Battle.commands、战斗执行会话、GameStore 快照、RunStorage、恢复命令、recoverable-pair 和现有随机流；核心抽象的新增必须能说明实际收益与维护/运行成本。
