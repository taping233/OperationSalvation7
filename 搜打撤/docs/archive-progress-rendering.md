# 收藏室成就进度：单次渲染内复用

## 已验证的重复工作

收藏室 `achievementsHTML` 对每项成就输出列表进度和详情模板，最后再输出当前选中详情。旧实现每个位置调用 `achievementProgressText(id, base)`；该函数不是只计算一个id，而是每次构造全部进度表，扫描收藏、人物、伙伴和符文，并重新读取背包/安全格容量。

当前真实目录26项，因此一次渲染产生 `2 × 26 + 1 = 53` 次全量进度表计算。排序、状态过滤、已领取/解锁判定另有自己的调用，不属于此计数，也不在本改动中。

## 改动和安全边界

新增 `createAchievementProgressReader(base)`，在当前同步渲染内计算一次进度表，返回只读查询函数，供列表、详情模板和初始选中详情共同使用。兼容函数 `achievementProgressText(id, base)` 保留原来的即时读取语义。

没有跨渲染缓存。下一次打开、刷新、换档、替换data或原地更新进度都会产生新快照。空目录不计算进度，保持缺少进度端口时仍可展示空态。所有领取资格检查、奖励发放、存档写入、错误恢复以及点击后刷新仍走原路径，未修改或减少校验。新增函数只保存本次展示用数值，不回写游戏状态。

## 验证

独立小副本，使用相同模块环境和真实26项成就目录：

- 旧/新3种进度和领取状态的完整HTML逐字一致。
- 以实际调用的bagCap计数，全量进度表计算53→1；这是计算次数，不是耗时降幅或FPS证据。
- 7个定向文件64项通过，其中1项为临时before/after实验，不纳入正式源码补丁。
- 正式新增测试覆盖：真实目录一次计算、原地数据变化后重新计算、data/档位替换不复用旧值、未知id、空目录不访问进度端口、状态呈现和不调用奖励命令。
- 现有收藏室交互、奖励反馈、hub导航、Base/Meta与collection-room回归通过。
- 8组项目配置类型检查、定向ESLint、修改源码node --check通过。测试日志无console错误。

未运行全量测试、生产构建或真实浏览器性能采集。此补丁证明消除了重复统计，不声称降低具体毫秒数、消除长任务或提高FPS。集成后按原发布门执行并保留当前浏览器验证口径。
