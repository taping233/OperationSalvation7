# 视觉验收、迭代与性能

## 1. 先确定谁验收

用户授权自动整改且未限制检查时，执行本章。用户说“我来验收”时停止其排除的浏览器/测试操作，将未检查项交给用户，不能拿本指南越过用户。

默认使用项目允许的浏览器和工具。当前项目要求内置浏览器时，不因方便就启动外部 Chrome/Electron；已有性能脚本若会开外部窗口，先确认它是否在授权范围。所有注入、采样和文件操作遵守实际工具接口，不能捏造不存在的 API。

## 2. 获得可信的视觉证据

- 先确认资源已加载、字体稳定、进入动画结束，再截图；过渡中的半透明画面不是最终效果。
- 使用相同内容、状态、视口和缩放比较前后。不要用不同原画冒充框的改进。
- 原生尺寸看字体/细节，整页缩略图看构图。同图去色对照只用于辨别形体层级。
- 如果使用缩放 iframe，记录内部视口和外层缩放；不要将缩放图视为原生像素清晰度证据。
- 每次导航/HMR 重载后重新定位 DOM。不要继续点击旧元素，也不要把回到封面误判为功能消失。
- 用户正在操作时，保留其页面。独立页若共享 localStorage/存档也不等于完全隔离，检查不得修改用户游戏进度。
- 检查最终计算样式：字体、字色、背景、边框来源、缩放、滤镜、可见性；必要时追溯覆盖它的规则。

## 3. 验收矩阵

先覆盖下表的关键代表组合，不默认做全部笛卡尔积。根据真实内容和设备增加高风险案例。

| 轴 | 最小代表案例 |
|---|---|
| 尺寸 | 主用桌面、较窄桌面、项目支持的最小屏；若项目只支持桌面，不扩成移动端重构 |
| 数据 | 普通、高阶、特殊分类；最长名称、多行正文、缺图/加载中、无匹配结果 |
| 状态 | 初始、悬停、键盘焦点、选中、禁用、筛选后、详情打开、退出 |
| 路径 | 进入→筛选→浏览→选中→放大→编辑/交互→关闭→返回 |
| 异常 | 连续点击、快速关闭重开、来源滚出视区、缩放/改尺寸、请求失败 |
| 动态偏好 | 项目支持时检查减少动态效果；不依赖动画才能看懂状态 |

例如照片库的首轮有效组合：普通桌面整页、高阶同图对照、桌面详情与收回、窄屏长名称、空结果、滚动追加。不要只看一张最大尺寸、最短名字、最好看的传奇照片。

## 4. 硬门槛：任一失败就不能宣称完成

| 门槛 | 具体通过条件 | 失败后先做什么 |
|---|---|---|
| G1 资源 | 关键图/字体/框可达，格式正确，无缺图占位冒充成品 | 检查服务、路径、解码、实际 CSS |
| G2 布局 | 主功能无遮挡，文字无不可接受溢出，无新增意外横向滚动 | 查容器尺寸、断点、盒模型与滚动根 |
| G3 字体 | 原生尺寸可读，角色层级明确，要求保留的语义颜色存在 | 修字号/字重/对比/字体加载，再减背景噪声 |
| G4 身份 | 同对象跨表面维持等级与框式；等级和选中可区分 | 查共享映射和组件作用域 |
| G5 连续交互 | 进入、筛选、选中、开关、返回可完成；编辑区不误关闭 | 修事件边界、来源位置和中断处理 |
| G6 风格约束 | 明确用户要求未回退，材质/光向/按钮语言一致 | 对照约束表逐项恢复 |
| G7 性能 | 有效场景下没有未经解释的重大回退，原有优化未被破坏 | 定位网络、解码、布局、绘制或合成来源 |
| G8 证据 | 检查确实运行，条件与结果匹配；未测内容明确标出 | 补必要证据或标待验收，禁止捏造 |

功能测试不能证明 G3/G6；一张漂亮截图不能证明 G5/G7；网络 200 不能证明 UI 已正确显示。

## 5. 软质量：按锚点评价，不拿平均分掩盖缺陷

给清晰度、满足感、统一性各记 0～3 级，只作内部排序：

- 0：结构或阅读有明显问题，核心目标未成立。
- 1：能用，但大量默认控件/平面块/风格断层，用户指出的主要问题仍可见。
- 2：主次和工艺体系成立，小尺寸仍清楚，跨状态一致；剩余为局部打磨。
- 3：重要部件细节与整页互相支持，素材和字体有足够完成度，没有明显突兀区域。

全面整改可将各项至少 2 级作为内部交付底线，用户要求的重点应达到对应明确标准。分数必须附截图中的具体理由，不是与成熟商业游戏等价的认证，也不能代替用户认可。

## 6. 每一轮怎么改，什么时候停止

1. 从矩阵取当前切片，获取稳定证据。
2. 找最多三个最影响阅读/质感/连续性的缺陷，按严重程度排序。
3. 每个缺陷写一个可证伪假设：例如“索引纹理对比过强导致字不清”，而不是“再高级一点”。
4. 修改对应变量或资产，不顺手重排无关模块。
5. 先重查失败点；若共用素材/组件改变，查它的代表调用处；无关已通过场景不重复。
6. 问题解决就标记并继续，不再以“还能优化”为由无限加工。
7. 同一修法两轮不改善，回到实际来源重新诊断。生成失败就改规格，CSS 不生效就查层叠，图片不清就查缩放和源尺寸。

一轮建议报告形式：`A04 未通过：缩略图雕花压成细线 → 增大角件主形并保留安静中段 → 同图220px下可辨；G4通过，窄屏仍待查。`

重大未解决项不得隐藏进“后续建议”然后宣布完成；真正无法继续时明确阻塞、已做工作与缺少什么。

## 7. 测试范围与验收频率

- 纯 CSS、文案、图片：按项目约定做视觉检查，不机械跑全部单元测试。
- 修改点击关闭、懒加载、焦点、选择状态等 JS：运行对应定向用例，并检查真实交互。
- 涉及公共组件：检查代表调用方，特别是用户要求保持原样的页面。
- 全量测试/构建只按项目规定在收尾或公共层变动时执行；存在其他任务未提交修改时尤其不能擅自 build。
- 中间只做解决不确定性所需的最小检查；整批完成后集中相关回归，避免每改一行就全量验收。
- 用户要求“都改完统一测”时，保存问题清单先实现；用户要求“我验收”时交付待验收项。

## 8. 性能检查必须先有可比条件

记录：设备、显示器刷新率、浏览器/运行方式、CSS视口、DPR、页面缩放、对象数量、缓存冷热、窗口前后台、采样时长和操作脚本。

如果基线已经丢失，就写“只有当前值，没有有效前后比较”。不能拿历史其他机器或不同分辨率的数据证明无回退。

将“渲染器实际绘制耗时”“JS/布局/绘制成本”“浏览器帧间隔”“最终显示帧率”分开。rAF 回调频率并不等于屏幕实际呈现 FPS；页面不动时减少绘制也不代表掉帧。

## 9. 可直接照做的采样流程

使用现有可信的性能工具或项目开发入口；没有时才增加最小的开发态采样，不能向正式用户流程塞性能面板。

1. 建立固定场景：同一筛选、同一排序、同一数据量、同一视口。关闭非必要干扰，但不擅自结束用户应用或修改系统设置。
2. 分开检查冷启动/首次访问和暖缓存；不要把第一次网络下载变快当成渲染优化。
3. 连续滚动一段固定路径，上下各一次，经过图片解码和批量追加点；避免只测空闲。
4. 连续切换若干选中对象、改变一次筛选、开关大图；记录具体操作数量。
5. 如果问题与长时间浏览有关，再滚到列表后部或完整数据集，返回顶部，观察 DOM/图片解码/内存是否持续累积。
6. 使用工具支持的采样方式记录帧间隔分位数、长任务、布局/绘制时间、加载耗时、DOM/图片数量与内存指标。
7. 初始可采用每场景约20～30秒、3轮同条件采样，比较中位结果；这是建议起点，不是必须对每个小改耗时执行。
8. 测量期间页面需处于工具支持的有效活跃状态。后台限速、失焦、视口不符、样本太少、采样进程提前退出都应判为无效或不确定。
9. 只在测量有失败、数据矛盾或代码再次改变时追加轮次，不做无止境基准循环。

若项目禁止外部浏览器且现有工具无法采样某指标，保留边界，报告“该指标未测”；不能绕过限制，更不能编造通过。

## 10. 记录哪些指标，怎样解释

| 指标 | 要记录什么 | 不能由它推出什么 |
|---|---|---|
| 首屏/可操作时间 | 相同起点到内容出现/可交互的时间；分冷暖 | 加载快不代表滚动稳 |
| 帧间隔 | p50/p95、慢帧占比、样本数、刷新率 | rAF间隔不直接等于GPU呈现FPS |
| 长任务 | 支持时记录大于50ms任务的数量、总时长、触发场景 | 没长任务不代表GPU/合成无瓶颈 |
| 图像 | 请求数、显示/解码尺寸、可见范围与预加载范围 | 文件KB不等于解码内存 |
| DOM | 初始数量、追加数量、后部浏览数量 | DOM少不保证每节点绘制便宜 |
| 内存 | 指标来源、滚动/开关前后、是否趋于平台 | JS heap不能代替GPU/原生图片内存 |
| 渲染器 | 如果有Canvas/WebGL，记录绘制次数与耗时 | 地图绘制通过不证明图库DOM性能通过 |

60Hz 的一帧时间约16.7ms、120Hz约8.3ms，这是时间预算参考，不是每台设备都应达到的承诺。优先采用项目已有且适用于当前 UI 的预算。

项目没有预算时，在改动前记录一个临时约定：主用设备、目标刷新率、允许的交互延迟、慢帧阈值、相对回退容忍度。例如相同场景 p95 回退约10%即可触发调查；它只是调查阈值，还须排除自然波动，不能被写成通用合格线。

`decodeBytes≈宽×高×4` 可估算常见RGBA单张解码内存量级，不是所有缓存/纹理实际占用。例如448²约0.77MiB，1792²约12.25MiB；不能用压缩文件只有几十KB解释全量原图常驻安全。

## 11. 出现性能问题，按来源修

| 证据 | 优先调整 | 不应先做 |
|---|---|---|
| 原图解码/内存暴涨 | 列表缩略图、有限预解码、实际视口根、缓存上限 | 降所有字体和图片到模糊 |
| 滚动追加出现长任务 | 分批、局部更新、避免反复全量排序/构建 | 不看调用就给所有节点加will-change |
| 布局抖动 | 稳定图片宽高/比例、减少同步读写布局 | 用阴影或动画遮掩位移 |
| 重绘/合成昂贵 | 缩小模糊/滤镜作用域，去除全墙常驻特效，静态纹理复用 | 为了质感给每张图套多层大面积滤镜 |
| 大图开关卡顿 | 只为当前对象加载高分辨率，检查解码与动画来源 | 提前解码整个相册原图 |
| 滚到后部持续变慢 | 查DOM累积和解码池；必要时再考虑虚拟化 | 未测量就引入复杂虚拟列表 |
| 服务停了/资源404 | 恢复服务或修路径 | 当成性能问题重写渲染器 |

优先保留：分批渲染、缩略图、懒加载、异步解码、可见区附近预热、局部更新与图片比例占位。是否存在这些措施要查真实代码，不得依据旧交接认定。

## 12. 结果写法

正确：`在指定桌面条件下完成3轮滚动采样，p95未见超出波动范围的回退；未测低端移动设备和完整长期内存。`

正确：`相关功能测试通过；美术与帧率未检查，老板接管验收。`

错误：`测试39项全绿，所以界面达到炉石水准且完全不卡。`

错误：`性能脚本退出码0，但没有报告；判通过。`

每份证据说明它能证明什么，不能证明什么。交付无需机械报告全部指标，但不能省略会影响用户判断的缺口。
