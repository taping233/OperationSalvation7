# 卡牌规则结构化迁移计划（Vite）

日期：2026-09-23。状态：按模块实施中；目前只迁移了少量代表卡，完整卡库尚未验收。范围仅为 `搜打撤` Vite 版。

## 1. 目标与边界

目标是让卡牌的可打出条件、费用、目标、触发时点和结算效果由明确的数据决定。`desc` 保留为玩家阅读的描述，修改措辞或标点不应改变已迁移卡牌的行为。迁移前后，现行卡牌的费用、伤害、触发顺序、普通战与 BOSS 战差异，以及玩家已有存档的实际结果应保持一致；发现现行实现与定版规则冲突时，另列规则问题，不在结构迁移中顺手改玩法。

本计划不覆盖 Godot、Unity、桌面 EXE，也不承担战斗 UI、美术或结算系统重做。`game/data/cards-sync.json` 是生成数据，不能手改。删除旧解析代码、改同步版本或迁移 key、提交、推送和发布均在实际实施时按项目约束单独核对。

## 2. 当前代码事实与风险

| 路径 | 当前职责 | 与描述文字的耦合 |
| --- | --- | --- |
| `game/src/cards.js`、`cards.rules.js`、`cards.sync.js` | 卡牌存储、播种、字段推导与迁移 | `dmgType/dmg/draw/infuse/heal/armor` 缺失时可由 `desc` 推导；出售资格也可能读描述。 |
| `game/src/battle.rules.js`、`battle.card-cost.js` | 目标、可打出条件、动态费用 | 通过正则判断群体、自身/敌方目标、牌库限定、手牌代价及费用变化。 |
| `game/src/battle.effects.js`、`effect-steps.*.js` | 拆分触发时点并逐句结算 | 将自然语言切句，再按有序正则步骤匹配；步骤顺序和 `did` 门控会影响语义。 |
| `game/src/battle.resolution.js`、`battle.engine.js`、`battle.core.js` | 单卡结算、装备、注能和回合事件 | 结构化数值与描述正则混用；还有按卡牌 `id` 特判、延迟保存文字后再次解析的路径。 |
| `game/src/game.bag.js`、`base.js`、`cards.rules.js` | 背包道具、仓库资源、钥匙计数和出售 | 回复/复原/资源数量、可出售标记仍会解析 `desc`；部分分支按卡名或 `id` 特判。 |
| `game/src/game.cardslib.js` | 制作坊编辑 | 可填写数值词条，也可手写 `desc`；保存到卡牌对象。 |
| `tests/card-audit.test.js` | 未识别句式审计 | 能拒绝新增未知句式，但逐句模拟不能代替完整出牌或跨回合验收。 |

定版卡牌、历史批次、`localStorage` 旧卡和局内持有卡共同构成运行时数据。`ensureCardsSyncLive()` 按稳定 `id` 覆盖整卡，历史批次也可重播。因此只给新卡增加规则字段、只改一处静态表，均不能完成旧档迁移。老板已明确后续通常在代码层修改卡牌，制作坊不承担新规则创作；现有手写描述入口可关闭，但旧存档仍需安全载入。

## 3. 迁移原则与数据契约

1. **稳定 `id` 标识卡牌，规则保存在现有卡牌记录内。** 定版数据继续使用既有同步入口，历史批次仍以定版 `id` 解析；不另建一张按名字或描述查找的规则表。
2. **每张卡的每个规则域只有一个执行权威。** `rules` 中已声明的可打出条件、费用、目标或某个触发时点只走结构化路径；未声明的域暂走旧路径。同一触发时点的整段效果必须原子迁移，不能在一次出牌中并跑新旧效果，再靠 `did`、日志或去重抵消重复结算。
3. **保留现有数值字段的含义。** 第一版结构化规则引用 `dmg/dmgType/draw/heal/armor/infuse/cost` 等已有字段，不重复录入同一个基础数值。条件附加值、次数等确需独立表示的参数才写进规则步骤。展示角标从同一数据投影，不再从 `desc` 反推已迁移卡的规则。
4. **顺序写成数据顺序。** 触发时点、条件、目标集合、操作及其前后关系必须可表达当前结算顺序；特别核对伤害→击杀→追加效果、注能先付代价、沉默、抽牌与延迟效果。
5. **规则版本显式且可校验。** 无版本或未知操作不能静默回落到描述解析。卡牌定义、保存、同步和载入各入口都应得到同一校验结果。

拟采用卡牌内的 `rules: { version: 1, triggers: ... }`。下例只说明数据形状，操作名和完整字段在阶段 1 用真实卡牌验定；其中基础伤害引用已有 `dmg`，不会再存一份数值：

```js
{
  id: 'example-card',
  dmg: 3,
  dmgType: 'attack',
  desc: '对目标造成 3 点攻击伤害。',
  rules: {
    version: 1,
    triggers: {
      onPlay: [
        { op: 'damage', amountField: 'dmg', target: 'chosenEnemy' },
      ],
    },
  },
}
```

首版只为现有玩法定义所需操作，不把中文文本做成另一套通用脚本语言。规则域的存在与否决定新旧路由，不能把空数组误判为“尚未迁移”；空数组表示该时点明确无效果。无 `rules` 的旧卡暂保留旧执行器；何时停用由覆盖清单和验收结果决定。跨域约束（如目标预检与实际效果目标）由校验器检查。

## 4. 按先后顺序实施

### 阶段 0：冻结行为基线并列出迁移清单

**依赖：** 无。开始前重新核对 `git status --short`、HEAD 和相关文件归属；已有并行改动不能覆盖。

**工作：**

- 以当前现役卡库为准，按稳定 `id` 列出每张卡的结构化字段、描述触发点、文本执行步骤、使用场景及旧档来源。扫描 `desc` 的所有规则调用点，分成展示、字段补全、预检、费用、目标、立即结算、延迟/被动、背包道具和基地经济规则；记录动态构造文字的路径。
- 给每个规则族选真实卡牌作为行为基线，记录行动顺序、费用、目标、状态、牌区、日志和最终数值。覆盖普通战、BOSS 战、注能成功/失败、沉默、击杀、回合开始、装备/道具。
- 将已知未识别句式按卡 `id`、条件和原因归档，区分“逐句审计缺少上下文”与“真实玩法尚未实现”。不把识别成功当作实装证明。
- 核对 `cards-sync.json` 条目数、历史快照、退役列表和新档/旧档播种顺序，留下可比较的基线；不运行会写入该生成文件的命令。

**产物与通过条件：** 一份可追踪的 `id → 文本依赖 → 预期行为 → 对应测试` 清单；高风险卡的当前行为可重复。未核实的玩法标为待定，不先替它定规则。

### 阶段 1：定下最小规则模式与校验器

**依赖：** 阶段 0 清单。

**工作：**

- 用一张基础伤害卡、一张费用条件卡、一张注能卡和一张跨回合卡检验 `rules` 所需的触发、条件、目标、操作与顺序。明确数值字段的引用方式、卡牌自身与敌方集合、随机性来源、失败条件及跨回合记录格式。
- 在卡牌装载边界校验版本、操作名、参数、引用字段、目标和时点；错误要指出卡 `id` 与具体规则位置。避免把非法规则当作“无效果”或默默交给文本执行器。
- 定义执行器的输入输出端口，复用现有 `battle.resolution.js` 的状态读取和领域操作；先不改卡牌 UI 或整个战斗运行时。

**通过条件：** 示例卡的结构化规则能在内存中通过校验；无效版本、未知操作、缺失参数明确失败；没有第三份定版规则表，也没有新增依赖。

### 阶段 2：先迁玩家出牌前的判定

**依赖：** 阶段 1。

**顺序：** ① 可打出条件 → ② 手牌/注能代价 → ③ 动态费用 → ④ 目标与群体范围。每小步同时接通预检和实际执行，避免按钮允许出牌而结算失败，或预检拒绝合法牌。

**工作：** 对迁移卡从 `rules` 计算结果；未迁移卡暂用原判定。优先处理现有 `battle.rules.js`、`battle.card-cost.js` 和 `battle.engine.js` 的相关调用点；按精确卡 `id` 比较迁移前后结果。群体牌的“拖向任意敌人”和“可直接打出”差异要用交互测试验证。

**通过条件：** 同一手牌、战斗状态与目标下，迁移前后费用、合法性、提示理由和指向一致；只改 `desc` 的措辞不改变这些结果。

### 阶段 3：迁立即结算效果

**依赖：** 阶段 2 对目标、费用和合法性的稳定接口。

**顺序：** ① 基础伤害和多段/群体 → ② 回复、护甲、抽牌/普通战初始攻击替换 → ③ 诅咒与祝福状态 → ④ 击杀后效果、发现/生成/复制及道具。每一族从少量代表卡扩到该族全部现役卡，保留结算次序。

**工作：** 将相应卡的 `rules` 放进既有卡牌数据来源，执行器通过领域端口结算。一张卡的 `onPlay` 必须一次覆盖该时点的全部效果；若它还包含后续规则族的操作，整张卡的 `onPlay` 延后迁移。已迁移时点完全绕开 `splitEffectClauses` 和文本步骤表，未迁移时点继续旧路径。按卡 `id` 逐项处理当前专用特判，先确认它属于定版差异还是旧兼容修补。

**通过条件：** 代表卡在相同随机种子和战斗上下文下，迁移前后伤害、状态、牌区、资源、日志关键事件及调用顺序一致；同一效果只触发一次。现有未支持项不能仅靠把它写进 `rules` 宣称完成，必须有真实结算断言。

### 阶段 4：迁触发、持续与跨回合效果

**依赖：** 阶段 3 的结构化操作。

**顺序：** ① `onDraw` / `onConsume` / `onInfused` → ② 战斗开始与装备主动技能 → ③ 本局持续和每回合开始 → ④ 注能变体、沉默、重复释放及其他组合条件。

**工作：** 延迟队列保存稳定的操作数据、来源卡 `id`、必要的施放快照和剩余次数；处理“登记时取值”与“触发时取值”的区别。不能再仅保存一段中文，下一回合重新解析。逐项保留现有触发顺序和取消语义。

**通过条件：** 跨回合、换目标、原卡离场、战斗结束/重开及读档后不会多触发或漏触发；普通战与 BOSS 战差异和注能先付代价保持基线。

### 阶段 5：迁背包、基地与经济规则

**依赖：** 阶段 1 的数据契约；排在战斗规则之后逐项处理，以免同一张道具卡在战斗和背包中使用不同口径。

**顺序：** ① 背包道具的回复、复原和资源发放 → ② 仓库材料种类/数量与钥匙计数 → ③ 出售资格及相关经济判定 → ④ 仍有规则意义的图鉴数值展示。保留仅用于日志、剧情和卡面阅读的描述使用。

**工作：** 复用卡牌内的结构化字段或规则操作，让背包、仓库与战斗取同一数值；按稳定 `id` 处理定版特例。对出售资格区分显式 `sellable`、历史描述备注和缺省值，先录下旧档行为再迁移。核对材料折算、宝藏大门钥匙数、道具使用后卡牌去向及容量边界。

**通过条件：** 修改已迁移道具/资源卡的 `desc` 不影响使用效果、资源数量、钥匙计数或出售资格；新档和旧档的背包、仓库结果与基线相同。

### 阶段 6：存档、同步与制作坊收口

**依赖：** 阶段 1 的校验器；与阶段 2～5 的规则族一起逐批做，不留到最后一次性补救。

**工作：**

- 对固定卡按稳定 `id` 将已定版 `rules` 进入现有生成/播种流程，核对同步脚本输入与输出、版本变化、退役列表和历史批次重播。只有确定旧档更新口径后才执行同步；生成文件不手改。
- 对持有卡快照、旧 `localStorage` 卡库、局内卡牌和待结算效果制定显式迁移：旧记录能安全解析的按卡 `id` 与版本补齐；无法确定语义的旧自定义文本卡保留兼容路径并标识，不假装已结构化。
- 关闭制作坊新增或手写规则的入口，保留已有卡牌的查看能力；在关闭前核对 `game.cardslib.js` 的并行文件归属。此阶段不设计新的自由文本规则编辑器，定版卡牌从代码层录入。已存在的自定义卡按旧数据兼容，不因关闭入口而从存档删除。
- 保持玩家已修改的卡牌字段与定版同步之间现有的覆盖/保留约定；分别验证新档、旧档首次启动、历史批次重播和重复启动。

**通过条件：** 旧档不丢卡、不复活退役卡、不重置玩家自定义内容；新规则持久化后再次载入等价；未知规则版本或无法安全转换的记录给出明确诊断。

### 阶段 7：关闭文本规则依赖并收尾

**依赖：** 阶段 0 清单中的现役规则已迁完；阶段 2～6 通过。

**工作：** 逐项移除已无调用者的规则正则、按名字特判和旧效果步骤；兼容旧档所需的解析只保留在明确的旧数据转换边界。重新检查所有 `desc` 读取点，证明运行时战斗规则不再由展示文字决定。同步更新 `docs/architecture.md`、`docs/rules.md`、`docs/quality-gates.md` 中受影响的契约说明。

**通过条件：** 对所有已迁移现役卡批量改写或清空 `desc` 后，其合法性、费用、目标和战斗结果不变；卡面显示仍使用原文案；旧档转换测试通过。删除代码或文件前列出精确路径并取得项目约束要求的同意。

每批先跑相关定向测试并记录卡 `id` 与结果；改公共规则架构或收尾落库前，再在无其他会话半成品的可构建工作区运行串行全量测试与项目质量门。测试通过不等于真实页面验收，浏览器验证必须单列证据。

## 6. 停止条件与实施顺序图

任一阶段出现以下情况时停止扩批，先定位该卡：迁移前后玩法结果不同且无定版依据；同一张卡同时走新旧结算；存档载入丢失规则或玩家编辑；新规则无法表达现有操作顺序；未识别句式被静默接受。修复后只重跑受影响族及必要依赖，不靠扩大例外清单过关。

```text
阶段 0 行为基线与清单
  ↓
阶段 1 最小数据契约与校验
  ↓
阶段 2 可打出条件 → 代价 → 费用 → 目标
  ↓
阶段 3 立即效果：伤害 → 回复/护甲/抽牌 → 状态 → 组合效果
  ↓
阶段 4 触发与跨回合效果
  ↓
阶段 5 背包道具 → 仓库材料/钥匙 → 出售资格
  ↓
阶段 6 旧档、同步、制作坊收口（随每一族同步推进并最终封口）
  ↓
阶段 7 描述独立性证明、旧解析清理、文档与完整验收
```

实施时每一族单独记录改动范围与测试证据；不把“卡牌文字已识别”“定向测试通过”或“全量测试通过”单独称为全卡库玩法完成。

## 7. 模块分工、依赖与合并验收

按下表拆给 `gpt-6-luna` 子代理，父任务负责代码复核、跨模块测试和实际页面验收。每个模块只改自己的文件；若要改同一张卡的定版数据或同一个迁移入口，按依赖顺序串行交接，不能并发覆盖。

| 顺序 | 模块与文件归属 | 交付物 | 父任务验收门槛 |
