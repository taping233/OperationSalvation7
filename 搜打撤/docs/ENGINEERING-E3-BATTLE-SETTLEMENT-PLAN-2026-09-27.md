## 1. 问题和本批目标

E1 已查清：普通远征胜利的 game.bag.settle.js 在 saving 阶段先 saveGame，再 Base.save；eggBattles 永久计数与本局完成状态分开写。WeakMap 中 runSaved/baseSaved/rewardsApplied 能保护同一实例重试，但不能在页面重建后恢复这两写之间的缺口。

本批固定解决这个最终结算检查点：有真实档位的普通远征胜利，完成整理后的 run 快照与本场基地永久计数在同一可恢复事务中落盘；失败与刷新后只能恢复到一致的前态或后态，同一事务重试不能再次发奖励或增加计数。范围涵盖现有四层远征的普通战/首脑战最终 settle 保存分支；龙巢、死亡、放弃和撤离既有公式不改。

不把战利品提前搬到基地。局内奖励仍属于 run；基地只按既有玩法写相应永久字段。保存完成点、玩法奖励数量和随机概率均不调整。本批不声称把胜利演出、开箱、整理、教学等整个交互过程变成一个大事务。

先以真实存储适配器的有界故障复现明确缺口；若当前代码已具备等价保证，报告证据给 Friday，不重复造恢复机制。复用 E1 及既有两批成果，不重做全仓架构审计。

## 2. 已定技术决策

1. 沿用模块化单体、JSDoc/checkJs、既有 recovery.commands.commitBaseAndRun 与 recoverable-pair；不另建事务日志、第二套存储、第二权威状态或数据库。
2. 用一个普通胜利领域命令准备不可变 attempt：slot/runId、真实读到的 expected base/run revisions、一次性 requestId、固定 fingerprint 输入以及完整 afterBase/afterRun。重试复用 attempt，不重新随机抽奖励、不重新加计数。
3. requestId 表示这次结算尝试，在同一重试/日志恢复中稳定；复用现有持久身份/检查点事实，不用 WeakMap 或渲染 token 冒充跨刷新身份。日志中的完整 after 快照是崩溃恢复依据。提交已成功或日志可恢复时重放收据，不从陈旧内存再造新事务；若需要额外存档身份字段，先向 Friday 说明不可复用的原因与最小兼容方案，获裁决后再改。
4. 事务准备不改写持久数据，不先调用 saveGame 把 run 写新后才开始 pair。复用原保存模型：如需构造当前 run payload，将现有 saveGame 的 payload 构造最小提取为可调用的无写盘构造入口，保持原字段、序列化、稳定检查点、随机流及旧接口语义，不维护两份字段清单。
5. 最终奖励计算沿用现有一次性阶段，提交失败期间保持互斥、可重试，不允许界面已放行后旧异步结果再投影。提交或恢复成功后，按已有 Base/RunStorage 刷新与 baseline 接口同步内存，明确实际owner；不能写回旧快照覆盖新档位/新局。
6. 沿用 pair 的日志→双存档→清日志恢复协议和生产身份校验；日志准备前失败保留旧稳定检查点，不承诺恢复还未持久化的中间动画。日志已保存后的任意断点要能恢复一致后态。遇第三值/版本冲突保留原始数据并阻断，不覆盖外来变更。
7. 沿用生产 Web Locks 约束：不支持时明确失败/保持待重试，不能为通过而退回无锁双写。无档位局保持原内存行为，不创建永久键。旧局、切档、同槽新run及同run revision变化均要拒绝陈旧 attempt。
8. ammoTaught 为独立一次性教学偏好，不因本批强并入战利品事务或改变展示时机；检查教学保存是否会覆盖尚未恢复事务，保证事务未完成前不继续该后续写入。该偏好写失败不得冒充核心奖励已失败或重算奖励。
9. 领域结果明确区分成功收据、待恢复失败、冲突和普通可重试失败，沿用既有结果形式。实际领域命令参数/结果用准确JSDoc约束并进入窄检查；外部run/base运行时校验继续保留。不可用any、关闭诊断或仅独立fixture接口伪造类型保障。
