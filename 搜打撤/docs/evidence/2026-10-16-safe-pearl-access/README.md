# 安全格珍珠盒直接打开

## 结果

已移除安全格珍珠盒的两处入口限制：安全格中的盒子现在能直接打开既有资源存取页，盒子不需要先移回普通背包。关闭按钮和 Esc 都返回原安全格页签。原有两栏 UI、存取行为、容量、卡牌归属与失败抢运逻辑原样保留。

本批完成未提交；没有操作浏览器、服务、build 或真实存档。父任务负责当前窗口实页验收。

## 依据与范围

- 现行 `docs/rules.md` 原先没有明确规定安全格盒子不能打开；只描述从背包打开和安全盒保护盒中资源
- `game/src/hub/game.bag.js:602,624` 原本分别用 `!safeFlag` 隐藏打开按钮、拒绝注册打开动作，限制位于 UI 入口
- 同文件 `openPearlStore` 从全部持有盒数计算容量；存入只置资源卡 `stored=1`，取出只删除资源卡 `stored`；均不改变盒子 `safe`
- `game/src/run/game.session.death.js:126-131` 的既有保护仍为：持有安全格珍珠盒时，`stored && !pouchOf` 的资源随盒抢运；本批未改这个条件
- `bagZone` 是既有模块状态。存取页不会修改它；`pearlBack` 调用 `showBackpack(true)`，自然回原页签。Esc 根据已有返回按钮的 `aria-label` 调用同一返回动作

本批源码仅改两行，见 [精确源码增量](source-change.patch)。`inventory-zoom.js` 前后 SHA 一致，未修改；其他已完成未提交改动未回滚或覆盖。

现行 `docs/rules.md` 仅珍珠盒同一行同步两项：背包或安全格均可直接打开；整叠取出按实际所需空间判定。其原“取出需要 1 个空格”无法覆盖既有多格整叠取出，已准确化；数值和实际判定不变。

## 已核对的现场解释

父任务现场为普通背包 19/27、基础通用容量 18、安全格持有珍珠盒。这个状态不能称为已经实测的死路：既有 `moveStackSafe` 从安全格取出只检查总容量，按代码 19+1≤27 仍可移回盒子。

允许安全格直接开盒改善的是不必要的搬出保护区操作负担。上述跨区移动只查总容量、未套用普通卡基础格限制，是独立既有口径缺口；本批仅记录，不改移动规则。

专测重现同一容量结构：安全盒直接存入一把钥匙后，19/27→18/27，盒子仍在安全格、资源卡仅增加 `stored`、UID 不变。此时新的普通卡依旧不能接收，因为通用接牌要求 `usedSlots < 18`。因此“腾一格”不能被写成“一次存入就能领取所有普通奖励”。

## 奖励页提示候选，未实施

候选文案：“可打开珍珠盒，将背包中的资源整叠存入，腾出背包空间。”

只有同时满足以下条件时，这句话才准确：

1. 当前确有未领取且容量受阻的奖励，尚未进入离开奖励确认
2. 玩家持有可实际点开的、未 `stored` 的珍珠盒；本补丁支持普通背包或安全格入口
3. 按既有公式计算盒子容量：全部持有珍珠盒数×9；已用张数为 `stored && !pouchOf`，不能把锦囊里的法术算作盒内资源
4. 普通背包存在实际可存入的资源堆，来源必须与 `cardStacks(false).filter(st => st.card.type === '资源')` 一致，不能把安全格资源或散装物资列为候选
5. 至少一个真实可操作资源堆可整叠放入剩余盒容量

第 5 项须匹配当前按卡名 `find` 的动作：同名资源被切成多个显示堆时，点击任何同名按钮都先取同名第一堆。例如前堆 3 张、后堆 1 张而盒内只余 1 张时，不能因后堆 1 张而显示“可存入”的肯定提示。候选判定应先按名称保留第一堆，再检查整叠张数是否放得下。

上述提示只承诺存在可用的腾格动作，不承诺腾出一个格后特定奖励就能入包。若希望进一步承诺“整理后可领取”，还须对合法存入后的投影状态调用共享收卡/奖励预检，不能重复实现新的容量规则。
