# 音频与角色帧生命周期实测

本轮实施两处运行时修复：静音或关闭音效时，首次输入不再初始化短音效库；角色会话取消时，停止等待 Pixi 资源并及时结束旧会话。原始文件、资源选择、画质和玩法不变。

| 受控负载 | 原实现 | 新实现 |
| --- | --- | --- |
| 保存全局静音后首次输入，每组五次交替样本 | 1 个 AudioContext，64 个 fetch/解码调用，64 个缓存 buffer | 均为 0 |
| 保存音效关闭后首次输入，每组五次交替样本 | 同上 | 均为 0 |
| 尾帧未完成，切换并离开 1/5/10 次，GC 后旧 owner 存活数 | 1/5/10 | 0/0/0 |
| 同条件，每批 100 次、四批交替负载的旧 owner 存活数 | 每批 100，累计 100/200/300/400 | 每批及累计均为 0 |
| 每 100 次 GC 后 JS heap 增量中位数 | 1,010,080 字节 | 183,680 字节 |

音频测试运行真实 `sound.js`、`SampleOnlyPlayer` 和事件入口，以受控 fetch/WebAudio/Howler 后端统计任务与实例。没有真实音频解码或设备播放；短段 `process.cpuUsage()` 中位数为 0，不能据此声称真实解码 CPU 收益。静音与音效关闭两组的受控墙钟中位数分别约 0.562→0.275ms、0.596→0.236ms，保留作复现记录。

帧测试运行真实 `battle.frames.js` 的 attach/hide、实际资源目录和新旧 `createFrameAssets`，只替换 Pixi 的纹理/绘制后端。首个 idle 完成后，三个共享尾帧 URL 保持 pending。每批按固定微任务数推进，用 `WeakRef` 观察 owner，经过两个事件循环轮次及显式 GC 采样。原实现仅在尾帧未完成期间累积；尾帧最终完成后，两版 owner、纹理及计时器均回到 0。heap 包含 jsdom 与夹具分配，是受此条件约束的 JS heap 观测，不是 RSS、GPU 或显存测量。CPU 中位数为 265→234ms/100 次，其中包含 GC 和 DOM 夹具，不作为设备上的 CPU 加速承诺。

`battle.frame-assets.js` 对每个底层 Promise 共用一组等待者，取消时移除等待者、解除 abort 监听并结算 null。底层加载不取消，资源所有权与晚到卸载保持原逻辑；新会话仍能接管共享 URL。无 controller 的调用沿用原等待语义。定向回归覆盖共享保活、晚到卸载、卸载中的取消、失败重试和成功/失败/取消时监听释放。

`sound.js` 仅调整 `kick()` 进入 `ensure()` 的条件。`assetUrl()` 调用、短音效目录/解码队列、音乐路径与 HTML5 后端选择不变。重新开启音效后，下次输入或 SFX 按原流程初始化一次；未就绪的声音仍不补播。公共 `ensure()` 行为不变，音乐首手势重试、独立开关、音量淡变及挂起上下文恢复通过现有和新增回归。资产消费者指纹由主会话统一审阅更新，本代理没有改动指纹。

相同 DOM 的重复 attach 在合成 1000 次调用中确实重复提交 1000 次绘制；外部快速路径模型可跳过这些提交。未证明游戏中存在这样的高频调用，因此本轮不实施该点。`frame-reattach.json` 的 candidate 是未落地的外部模型，不是交付代码收益。

新增回归 17 项，相关既有回归 61 项，共 78/78；生命周期 A/B 3/3；四个编辑源码/测试的 ESLint 为 0。验证命令与结果在 `validation.json`，完整样本在三个 JSON，生产与测试最终 hash 在 `source-inputs.json`。没有运行全量测试、build 或浏览器；本轮没有做原生音频/GPU/实玩验证。

复现：把 `harness/*.txt` 按去掉 `.txt` 后的文件名复制到 `.tmp/deep-perf-1018/resources/`，在仓库根先运行 `node .tmp/deep-perf-1018/resources/prepare-probes.mjs`，再执行 `validation.json` 中的指定 A/B 命令。准备脚本从本目录 `baseline/*.txt` 读取原始字节，只为音频基线重定向静态相对 import；新实现直接导入生产文件。脚本不覆盖已有 baseline，也不改生产源码。Node 必须支持 `--expose-gc`，使用本地已安装的 Vitest/jsdom/Pixi 依赖，无下载。
