# 普通跑局战斗胜率与刷新持久化

## 结论

真实 BattleSession 原本会调用 `noteBattle`，但 `agent.recorder.js` 的场次/胜场只在模块内存。普通 Run 保存和装载完全没有这些字段，正常刷新会丢掉此前战斗。数据页 `agent.data.js` 使用全部终局记录，`agent.stats.js` 按总胜场 / 总场次计算；不是只统计 Agent，也不是把死亡率误当胜率。

隔离实验使用真实 recorder、同一空白 JSDOM localStorage 和重新实例化的 ESM 模块：先6胜，重载后0场，再记首脑1负，终局成为1战0胜、胜率0%。这验证了源码缺陷及与父任务刷新时间线一致的失真路径；没有读取玩家页面或隐藏存档，未声称已经检查过玩家导出的真实 JSON。

另一个顺序缺陷：原 finish 先广播结束，再记战斗。同步终局回调能先记录并清零本局统计，使末场落入下一份内存。本轮把计数移到广播前，并用 battleActive 阻止相同 finish 重入。

## 实现

- 新纯叶模块 `agent.battle-stats.js` 维护有界战斗计数、末40场白名单快照及校验，recorder保持291行
- recorder新增 snapshotRunBattles / restoreRunBattles，门面对应暴露；终局 JSON 附 runId，CSV既有列不改
- createRunSavePayload保存runBattleStats，实际装载在身份预检采纳后恢复；newRun在出征准备成功后清零
- runId来自RunStorage身份；旧档缺失、坏统计、错runId归零，不猜造地图或历史日志中的胜场；恢复替换而不累加
- 隔离 devSample 不进入玩家计数；正常真人/辅助汇总算法不变。同一会话内恢复战斗统计不会抹去既有驱动/干预事实

本局0统计首存尚无runId时允许null；有身份后正常保存绑定。无法暂时读取身份时不清空已有绑定。不同runId不能把原内存计数盖章给另一局。

## 验证

最终相关回归共29文件192项通过：22文件161项覆盖保存、装载、终局、来源、架构；另7文件31项覆盖真实战斗、QA隔离及全卡审计。全卡268张硬失败0，原有3个条件性零效果提示保留。详见两个回归日志和 battle-stats-verification.json。

新增测试覆盖：真正模块重载+真实保存装载的6胜/1负=85.7%；真实BattleSession正常出牌6胜、首脑敌方攻击致死；重复读档、重复finish、倒地展示等待期重复提交；重复战斗检查点恢复不增场；新局和跨档分离；末40场/名字/编组限长、深克隆及白名单；旧档、非法计数、错身份、坏流水；QA/devSample不混入；同会话辅助来源不丢失。

ESLint7文件、syntax425文件、8组typecheck、docs461相对链接和diff-check通过。未运行整仓全量/build。父任务负责第二轮自然实玩和刷新验证。

## 历史数据边界

父任务首轮已经丢掉的胜场无法从之前没有保存的字段恢复；本补丁不修写首轮记录、不往玩家存档手工注入6胜1负。旧终局跑局记录仍保留原样，新一轮才建立完整的刷新统计证据。
