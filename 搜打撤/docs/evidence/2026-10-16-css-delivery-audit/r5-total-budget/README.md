# R5 CSS 总预算只读复核

## 核心判断

**本轮没有发现能在不改变现有视觉、级联及动画的前提下，一次补足 60.1 KiB 总 CSS 缺口的低风险方案。** 不建议把首屏拆分当总预算优化，也不建议继续以全局机械去重来承诺数十 KiB 收益。

R5 的 10 份发布 CSS，实际 Node gzipSync 合计 **200,836 B / 196.1 KiB**，原预算 **139,264 B / 136 KiB**，超出 **61,572 B / 60.1 KiB**。入口 index CSS 为 161,576 B；其余 9 份合计 39,260 B。`scripts/perf-budget.cjs` 对发布目录所有 `.css` 分别 gzip 后求和，异步及 `new URL()` 样式也计入；并非只统计首屏。

此前 18 份 CSS 的死 DOM 清退已在本轮 R5 输入中，未回退或重复计算。本轮只写本 `r5-total-budget` 子目录，保留上轮证据；不改生产代码、配置、预算、字体或许可证，不删除文件，不 build，不启动服务或浏览器。

## 三个可选择的方向

### 1. 小规模确定性整理，保护视觉优先

同一个发布 CSS 内，在同一条件、相同完整选择器、相同 important 下，**68 条同值后写覆盖声明**的内存模拟可再节省 **241 B**。示例包括 winter 与后续页面层中同样的宝箱 `border-radius:0`、已领取卡 `filter:grayscale(.7)` 等。只删早先确定被同值覆盖的声明，保留后写声明及文件、规则顺序。

若额外把逗号选择器拆成分支来证明覆盖，候选增至 94 条，收益 **311 B**；相对严格方案只多 70 B，不值得扩大选择器支持性审核。相邻同声明块 38 次合并只节省 **53 B**，也不值得专门引入优化器。

这些收益已扣除 5 份独立运行时 CSS 从既有“只压空白”切换到全语法压缩所带来的 98 B 控制组差异；不能把这 98 B 当重复删除收益。各项不能直接相加。

**建议：** 若要做一小批，先只选严格的 68 条候选，逐条映射源码并核对后写声明必定同步加载；不要用开发态加载先后或未来页面 CSS 来证明当前被覆盖。每条保留来源/目标属性证据，`@font-face`、关键帧、CSS 自定义属性以及复杂条件不碰。原 CSS 清退专测、相关页面样式专测和真实页面 A/B 均需保留。收益不到 0.3 KiB，对本次超预算没有实质影响。

### 2. 旧主题/页面层合并，先验证小域，收益不能夸大

允许“不同值后写覆盖”的宽松模拟：完整选择器方式 407 条、**2,443 B**；选择器分支方式 547 条、**3,192 B**；再加入 important 优先级与常见 shorthand 重置覆盖，620 条的示意上界约 **3,651 B / 3.6 KiB**。它们都是扣除上述 98 B 控制差异后的数值，**不是安全删除清单或已验收收益**。

剩余风险是后写值可能依赖 `var()`、不支持时的回退、shorthand 重置、分支选择器解析支持及 CSSOM。不能依据“文本后写”删除老值。原生全局皮肤里还混有标题、开发控制台、焦点、背包、宝箱、商店拒买反馈和动画，文件名不能当未使用的证明。

实际 R5 边际成本说明了结构：

- winter.css 单独占入口 gzip 边际 **16,597 B / 16.2 KiB**
- winter.css + ak-skin.css 两层整体的边际成本 **19,826 B / 19.4 KiB**
- 10 份基地历史及现行层整体的边际成本 **33,446 B / 32.7 KiB**

以上“边际成本”是隔离模拟把对应完整规则区间拿掉后的压缩差，**其中包含大量必需的存活样式，不能当可节省量，也不能相加**。即使错误地拿掉冬日/AK 两层全部内容，也只能覆盖总缺口的约三分之一。未测得可直接兑现的数十 KiB 重复主题收益。

**建议：** 真要推动总预算，先挑基地整备或宝箱一类稳定域，把最终状态的结构/视觉/交互正本合并，保留 hover、focus、disabled、读档恢复、关闭态和 reduce-motion，再清退仅被后写值覆盖的老声明。只在这一域拿到生产 build 的实际总 gzip 下降和浏览器视觉/动画等价证据后扩域。不能直接删 winter/base-camp，也不能对非相邻同声明块全局重排。

### 3. 基地连续尾段按需加载，只有首屏价值

复核了既有提案的 16 份连续尾段，R5 全部匹配：入口 CSS **161,576 → 136,822 B**，首屏减少 **24,754 B / 24.2 KiB**；延迟包 25,823 B。保序拆分后全部 CSS **200,836 → 201,905 B**，反而增加 **1,069 B**。原门禁继续失败。

21 份基地/选角整组的三槽拆分，首屏减少 40,004 B / 39.1 KiB，但总 CSS 增加 3,729 B。四份菜单皮肤单独拆分首屏少 7,756 B，总量增加 1,770 B。源码按页面加载在现有架构可做，但要为“提升首屏”单独决策，不能为总预算通过而做。

实施边界沿用上轮报告：固定原 CSS 级联槽位；hub 与直接选角共同等待；成功后再核导航 token；失败可重试；旧请求 finally 不清新状态；取消一个消费者不撤他人的共享样式；标题动效、共享卡面与运行时动画覆盖保持原顺序。单纯从 eager import 挪进动态 JS 会改变插入顺序并有 FOUC、跨页覆盖及首次动画风险。

## 排除的“便宜大收益”

- 每份产物内完整相同规则/整文件去重不是大头；同选择器、同值重复只有上述 241 B
- 15 组“长字面量提取为 CSS 变量”的内存实验，没有超过不替换控制组的正收益；常见方案反而增大 gzip。没有把含 var/env/attr/url 的值搬到根节点，避免改变变量求值及 URL 基准
- 同条件同完整声明块，跨非相邻规则的重复理论上只有约 22 KB 未压缩声明文本；最大组是 `display:none` 和 `content:none`。压缩量更小，且它们分布于不同页面状态，不能搬到统一位置后声称级联不变
- 没有通过改预算、隐藏扩展名、把 CSS 塞进 JS、移除许可证或改变统计口径制造通过
