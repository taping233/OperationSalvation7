## 缺陷

### C-01 / P1：污染祭坛手动复原页无法选择或离开

1. 第四层祭坛献祭三张背包卡，选择“复原 3 张消耗卡＋回复 10 血”。本次当时背包 12/16，口袋 10 张，其中页面列出 7 张可复原。
2. 点击充能射线、冰刺、闪电链卡名；再用真实卡面坐标点击充能射线。点击“继续旅程”，另试 Esc。
3. **期望**：每点一张回到背包并扣减可复原数；继续旅程返回地图。
4. **实际**：生命 28→35 成功，卡片、剩余 3 次与背包 12/16 均不变；继续按钮和 Esc 留在同页。浏览器 error 日志为空，不据此推断没有运行异常。
5. 正常刷新续档可回到祭坛地图；背包仍 12/16、口袋仍 10，三张复原未执行。重访祭坛只播放过场后回地图，不再给奖励页。没有获得重复奖励。

证据：`C-altar-restore-inert-before-ax.txt`、`C-altar-restore-inert-after-ax.txt`、`C-altar-restore-inert-final.png`、`C-altar-refresh-recovered-ax.txt`。影响范围限定本次祭坛手动选择流程；其他线的复原药水自动路径可用，不能泛称所有复原失效。

### C-02 / P2：通用容量与资源专用容量混合显示

1. 携带珍珠盒，通用背包已占 16 格，界面总数显示 16/25。
2. 第八战战利品页选择连射详情，或点击全部收下。
3. **期望**：说明通用格已满、剩余 9 格仅容资源；玩家在领取前能理解该卡为什么放不下。
4. **实际**：只显示“16/25、预计可收 0 张、3 张放不下”；连射详情仅称“当前放不下”。批量操作真实结果为 0 入包、3 散落。
5. 珍珠盒规则确实为 3×3 格仅装资源；祭坛献祭珍珠盒等三牌后分母 25→16，主包 15→12。因此问题是容量语义未分开呈现，**没有证据认定算法错误**。

证据：`C-reward8-capacity.png`、`C-loot-refused16of25.png`、`C-loot-refused16of25-ax.txt`、`C-loot-scattered16of25-ax.txt`、`C-backpack-help-ax.txt`、`C-altar-denominator16-ax.txt`。

玩法的核心取舍可读：小怪会消耗可用招式、营火与祭坛决定后续牌量，首脑每回合军威增加迫使玩家处理防御与伤害。此局从“16/25 还有空位”的预期落到无法收牌，再因祭坛故障缺三张复原，玩家容易把功能错误误解为构筑失败。首脑编组把不足 15 张与初始攻击不足明确列出，这一层说明比奖励容量提示更可靠。

对照 `ART-DIRECTION-BRIEF.md`、`VISUAL-BIBLE.md` 与基地参考原则：冬境街区的大形现代构件、积雪边缘和开阔战斗带符合未来冬日城市方向；角色轮廓完整，敌我对象、意图与状态位置稳定。基地单一整备动作、边缘底栏、人物完整大图、交易账面和扩建前后对照值得保留。仓库卡牌信息重复于卡面与下方名称，长规则在当前窗口的小卡上仍需详情才能阅读；这是密度取舍，不应以更小字号继续堆规则。基地背景比当前人物/卡面更写实、细节更密，可在未来统一画风时减少碎纹理，保留房间结构与光照。

动效与加载只作定性观察：入城、遇敌、首脑和奖励有短过场；UI 可在画面转场时先进入新状态，单次截图可能仍是前一画面或暗场，之后正常显示。本线未取得可用于性能归因的帧率、网络或计时数据，没有持续加载卡死的证据。首脑战中一次注能点击在过渡期未选中，核对新状态后再次选择成功，不列为独立缺陷。

可删减候选：减少反复出现的同类遇敌/搜刮标题过场；折叠奖励页重复的总数说明，优先保留实际去向；已访问节点不用全变成缺少身份的“空白节点”，可保留旧地点小标签帮助回找营火与商店。庭院的池景、雨圈和投喂反馈已有完整焦点，不必加事务块。
