# 现行复杂卡消费者迁移补齐

生产已冻结，仅修改 `StructuredRules.cs`、`BattleSession.cs` 与新增 `BattleComplexSourceSemantics.cs`。以现行 JS 的真实调用链转译，共享消费者覆盖全部对应声明，卡库及 UI 不改。Root 负责后续 Unity 原生验收。

## 修复与证据

- 花开两面的随机祝福沿 `choice-semantic-operations.js`，依次处理玩家与活着的数值随从；优先缺失祝福，净化只在有诅咒时进入缺失池，护甲分支增加 5。使用原 `generation` 随机流。
- 灵能召唤产生的临时卡保留 `noInfuse`，共用注能豁免判定同时控制材料数和真实结算上下文，因此“免材料”也视为已注能。
- 精神控制保留受伤敌人的生命、攻击、法伤、行为、防御、状态及待恢复攻击条目；不继承敌方标记。随从在原回合顺序中结毒、死亡并衰减计时状态，伤害沿正式表现队列发出。
- 真实灵能召唤转录同时证明发现候选算法不一致：源从完整池重复抽样，重复 ID 或名称最多重抽 40 次；Core 原为无放回抽样。现共用发现入口沿完整源算法，seed 1 第三候选一致为龙焰射线。
- 同一花开两面的后续回合证明：另一门的随机诅咒也应走 `generation`；持续任务应保留相对注册次序，不能每次移到队尾，否则两门同时生效时随机调用顺序会改变。

`source.mjs` 使用真实现行 `Cards` 和 `createBattleEngineInstance`，通过只读 Vite SSR 加载；`Tests.cs` 使用安装后的新生产 Core 快照。36 条向量状态均相同，门效果的随机流终态也一致：24 个首回合祝福样本、8 个两门自动开启后第 3/4 回合样本、3 个带状态征召后的两回合样本、1 条灵能召唤→真实候选龙焰射线（无需材料，造成 13 伤害）。

代表边界覆盖空祝福、已有祝福、唯一缺失护甲、仅净化候选、随从甲盾保留、中毒死亡、冻结和潜行到期。源探索最初等待发现后的忙碌状态时曾过早提交，现按真实忙碌解除后提交；失败诊断仍保留在历史运行日志，不作为已通过证据。

生产安装后重新复制快照，定向回归通过：1814 项现行目标及邻接、289 项预测与邻接、167 项卡语义、46 项支付边界、47 项目标边界。129 张单卡扫描保持 128 张投影完全一致；黑暗形态仍仅为已知 `discoverPlus` 内部存储位置映射，未报行为缺陷。
